# 10 · 工具协议与扩展体系

> **场景**：模型在每一轮采样中可以产出 `tool_use` 块，runtime 必须把这些 JSON 调用路由到正确的实现、流式回传进度、并最终把结果送回采样循环。本章拆解 grok-build 的工具系统：它既不是「一个巨大的 match」，也不是「每种工具写一份胶水」，而是三件东西的组合——**统一工具 trait**、**对象安全的派发契约**、**可插拔的扩展平面**。
>
> **阅读说明**：源码基准 `SOURCE_REV = d5a0335a47221e8c9519936cb693e9b6450227ec`。所有 `file:line` 均对应当前工作区代码。工具系统的三个基座 crate 是 `crates/common/xai-tool-types`、`crates/common/xai-tool-protocol`、`crates/common/xai-tool-runtime`；下游实现分散在 `crates/codegen/xai-grok-tools`（内置工具 + 注册表）、`crates/codegen/xai-grok-mcp`（MCP）、`crates/common/xai-computer-hub-core` + `xai-computer-hub-sdk`（Computer Hub）、`crates/codegen/xai-grok-hooks`（钩子）、`crates/codegen/xai-grok-plugin-marketplace`（插件/技能）。

## 第一层 · 简单框架（系统骨架）

工具系统可以压缩成一句话：**一个 trait 描述「一个工具是什么」，一个 trait 描述「怎么调用它」，一个 index 描述「去哪找它」，几个平面提供「它的具体实现」**。

```
                         ┌─────────────────────────────────────┐
                         │        模型一轮采样 (Sampler)         │
                         │   产出 tool_use { name, arguments }  │
                         └───────────────┬─────────────────────┘
                                         │ tool_id + args(Value)
                                         ▼
   ┌───────────────────────────────────────────────────────────────────┐
   │                    会话派发入口 (ToolDispatch)                       │
   │   async fn call(tool_id, args, ctx) -> ToolStream<TypedToolOutput>  │
   │   位置: crates/common/xai-tool-runtime/src/dispatch.rs:32           │
   └───────────────────────────────┬───────────────────────────────────┘
                                     │ 按 tool_id 路由
            ┌────────────────────────┼────────────────────────┐
            ▼                        ▼                         ▼
   ┌────────────────┐     ┌──────────────────┐      ┌────────────────────┐
   │ 内置 grok_build │     │   MCP 服务器群    │      │  Computer Hub / 其他 │
   │  工具注册表       │     │ (xai-grok-mcp)  │      │  扩展平面            │
   │ (xai-grok-tools)│     └──────────────────┘      └────────────────────┘
   └───────┬────────┘
           │ 每个工具实现 Tool trait，经 ToolDyn 类型擦除后挂入注册表
           ▼
   ┌───────────────────────────────────────────────────────────────────┐
   │  Tool trait: run (阻塞) | execute (流式)  类型擦除: ToolDyn          │
   │  位置: crates/common/xai-tool-runtime/src/tool.rs:36 / :306         │
   └───────────────────────────────────────────────────────────────────┘
```

四个「基座」概念 + 四类「扩展平面」：

| 概念 | 类型 / trait | 位置 | 一句话职责 |
|------|-------------|------|-----------|
| 统一工具接口 | `trait Tool` | `xai-tool-runtime/src/tool.rs:36` | 一种工具的「身份 + 描述 + 入参 + 出参 + 执行」 |
| 类型擦除层 | `trait ToolDyn` | `xai-tool-runtime/src/tool.rs:306` | 把泛型 `Tool` 抹平成 `Box<dyn ToolDyn>`，便于塞进一个 `Vec` |
| 对象安全派发 | `trait ToolDispatch` | `xai-tool-runtime/src/dispatch.rs:32` | 拿到 `tool_id + args(Value)` 返回流式结果，runtime 只认这个 |
| 可插拔搜索 | `trait ToolSearchIndex` | `xai-tool-runtime/src/search.rs:63` | 「给定一句自然语言，返回最相关的 N 个工具」 |

扩展平面（都通过上面四个概念接入，模型侧无感）：

1. **内置工具**：`crates/codegen/xai-grok-tools/src/implementations/grok_build/`，约 26 个（bash / read_file / grep / search_replace / task / todo / web_search / web_fetch / image_gen / …）。
2. **MCP（Model Context Protocol）**：`crates/codegen/xai-grok-mcp`，把外部 MCP server 的工具桥接成 `ToolDispatch`。
3. **Computer Hub**：`crates/common/xai-computer-hub-core` + `xai-computer-hub-sdk`，远程工具服务器经 `CompoundResolver` 聚合成本地 `ToolDispatch`。
4. **Hooks / Plugins / Skills**：`xai-grok-hooks`、`xai-grok-plugin-marketplace`，分别提供生命周期钩子、插件安装目录、技能发现与调用。

## 第二层 · 一个完整例子（全路径走读）

以「模型想读一个文件」为例，走完整条链路。我们只看主干，第三层再展开每一步。

```
① 模型采样产出 tool_use
   { name: "grok_build__read_file", arguments: { path: "src/main.rs" } }
        │
② 会话 turn 在 run_turn_via_sampler 中收集到 tool_use 块
   crates/codegen/xai-grok-agent/.../sampler_turn.rs:1142
        │
③ execute_tool_calls_batch 拿到一批 tool_use
   crates/codegen/xai-grok-agent/.../tool_calls.rs:494
        │  对每个 tool_use：tool_id = "grok_build__read_file"，args = {"path":...}
        ▼
④ 派发：CompoundResolver / InnerDispatchForResolver 实现 ToolDispatch::call
   crates/common/xai-computer-hub-core/src/inner.rs:56
        │ call(tool_id, args(Value), ctx) -> ToolStream<TypedToolOutput>
        ▼
⑤ 找到内置 read_file 工具，触发其 Tool::execute
   （默认实现把 Tool::run 包成单条 Terminal 流）
   crates/common/xai-tool-runtime/src/tool.rs:87  (execute)
   crates/common/xai-tool-runtime/src/tool.rs:101 (run)
        │
⑥ 工具实际读盘，产出 ToolStream:
   [ Progress(Text{...})? , Terminal(Ok(TypedToolOutput{ value, model_output })) ]
   crates/common/xai-tool-runtime/src/tool.rs:120 (ToolStreamItem)
        │
⑦ TypedToolOutput 回传采样循环，作为下一轮 assistant 消息的 tool_result
   crates/common/xai-tool-runtime/src/tool.rs:246
        ▼
⑧ 模型拿到文件内容，继续推理 / 产出最终答案
```

链路里最关键的一点：**模型侧永远只看到 `tool_id + args(Value) → ToolStream<TypedToolOutput>`**。无论工具是内置的、MCP 的还是远程 Hub 的，接口完全一致。这就是「扩展平面可插拔」的含义。

## 第三层 · 详细逐步说明（主链路拆解）

### 步骤 1 — 模型产出 `tool_use`

采样循环（`run_turn_via_sampler`，`crates/codegen/xai-grok-agent/.../sampler_turn.rs:1142`）把模型返回的 `SamplingEvent` 攒成一条消息。其中 `SamplingEvent::Completed`（`crates/common/xai-chat-state/.../events.rs:52`）是**提交屏障**——只有它代表一轮稳定结果，里面可能包含若干 `tool_use` 块。注意：流式 `Progress` 不进入这里，工具结果不在 token 流里逐步拼接。

### 步骤 2 — 收集并批处理工具调用

`execute_tool_calls_batch`（`crates/codegen/xai-grok-agent/.../tool_calls.rs:494`）拿到这一批 `tool_use`，逐个解析出 `(tool_id, args)`。它不关心工具来自哪个平面——它只调用统一的 `ToolDispatch` 契约。

### 步骤 3 — 派发契约 `ToolDispatch::call`

`ToolDispatch`（`crates/common/xai-tool-runtime/src/dispatch.rs:32`）是唯一被 runtime 调用的对象安全接口：

```rust
#[async_trait]
pub trait ToolDispatch: Send + Sync {
    async fn call(
        &self,
        tool_id: ToolId,
        args: Value,
        ctx: ToolCallContext,
    ) -> ToolStream<TypedToolOutput>;

    async fn call_terminal(&self, ...) -> Result<TypedToolOutput, ToolError> { /* 默认实现 */ }
}
```

`call` 返回 `ToolStream`，且**必须**以恰好一个 `Terminal` 收尾（不变量，见第四层）。`call_terminal` 的默认实现（`dispatch.rs:50`）只是把 `Progress` 丢掉、拿到第一个 `Terminal`；如果流里没有 `Terminal`，它报 `ToolError::custom("stream_no_terminal", ...)`——这是实现方违反协议时的兜底。

> 为什么需要 `ToolDispatch` 这一层？因为 `Tool` 本身是**非**对象安全的（它带关联类型 `Args` / `Output`）。runtime 不能在 `dyn` 上保留泛型，所以「给模型/给批处理器用的入口」必须是 JSON 类型安全的 `ToolDispatch`，而「具体工具作者写代码用的接口」是带泛型的 `Tool`。二者通过 `ToolDyn` 的 blanket impl 自动桥接（见步骤 4）。

### 步骤 4 — 类型擦除 `ToolDyn`

每个 `Tool` 实现都会自动获得 `ToolDyn`（`crates/common/xai-tool-runtime/src/tool.rs:306` + `:336` 的 blanket impl）。`ToolDyn::execute` 做三件事：

1. `serde_json::from_value::<T::Args>(args)` 把 `Value` 反序列化为强类型入参；失败则直接 `Terminal(Err(invalid_arguments))`，不进工具逻辑（`tool.rs:359`）。
2. 调 `Tool::execute(self, ctx, typed_args)`（`tool.rs:365`）。
3. 把 typed 输出 `serde_json::to_value` 成 `Value`，并调用 `out.model_output()` 抽出模型可见的 content blocks，组装成 `TypedToolOutput`（`tool.rs:370-389`）。

这一步是「泛型世界」与「JSON 世界」的唯一边界。

### 步骤 5 — 工具本体：`run` vs `execute`

工具作者二选一实现（`crates/common/xai-tool-runtime/src/tool.rs:79-111`）：

- **`execute`**（流式，默认实现在 `:87`）：包一层 `async move { terminal_only(self.run(...).await) }`。也就是说，**只写 `run` 也行**，默认就被包成单条 `Terminal` 流。
- **`run`**（阻塞，默认实现在 `:101`）：返回 `Err(ToolError::not_implemented(...))`。两者都不写 = 首次调用即失败， loudly fail。

流式工具（如要实时回传 stdout 的 bash）应直接覆写 `execute`，用 `with_progress(progress_stream, terminal_future)`（`tool.rs:218`）拼出 `[Progress*, Terminal]`。

### 步骤 6 — 流不变量与 `TypedToolOutput`

`ToolStreamItem<T>`（`tool.rs:120`）只有两个变体：`Progress(ToolProgress)`（零或任意多个）与 `Terminal(Result<T, ToolError>)`（**恰好一个，且永远最后**）。`TypedToolOutput`（`tool.rs:246`）携带 `tool_id` / `value(Value)` / `model_output(Vec<ContentBlock>)` / 可选 `chat_completion_output`。

> **MCP 不变量**：`model_output` 永远非空。默认 `ToolOutput::model_output` 会把 typed 输出序列化成 JSON 文本块，所以哪怕工具不复写，也能满足 MCP 的内容合规要求（`tool.rs:238-244`）。

### 步骤 7 — 回传与下一轮

`TypedToolOutput` 被批处理器收集为 `tool_result`，附回 assistant 消息，下一轮采样携带它继续。若工具返回 `Terminal(Err(e))`，错误同样作为 `tool_result` 回传模型（而不是中断整个 turn）——模型可以自我纠正。

## 第四层 · 补全所有逻辑与技术要点

### 4.1 三基座 crate 的职责切分

```
crates/common/xai-tool-types      → 工具描述/参数/能力/错误的「数据结构」
crates/common/xai-tool-protocol   → 线格式与握手 (PROTOCOL_VERSION)
crates/common/xai-tool-runtime    → Tool / ToolDyn / ToolDispatch / ToolSearchIndex / 流原语
```

- **握手版本**：`crates/common/xai-tool-protocol/src/handshake.rs:10` 定义 `pub const PROTOCOL_VERSION: &str = "1.0.0"`。任何「工具 ↔ runtime」桥接（MCP、Hub）都要对齐这个版本号。
- **类型层**：`xai-tool-types` 提供 `ToolDescription`、`ToolCapabilities`、`ToolId` 等，被 runtime 与所有实现 crate 共享，避免重复定义。

### 4.2 `Tool` trait 全字段

`crates/common/xai-tool-runtime/src/tool.rs:36`：

| 成员 | 默认 | 说明 |
|------|------|------|
| `type Args` | — | 反序列自 JSON 的入参类型（需 `JsonSchema`） |
| `type Output` | — | 出参类型（需 `ToolOutput`） |
| `id()` | — | 稳定身份，派发用它路由 |
| `description(ctx)` | — | 模型可见描述 + 入参 schema；可吃 `ListToolsContext` 做上下文感知 |
| `capabilities()` | `ToolCapabilities::default()` | 并发/作用域/帧上限等能力标志 |
| `has_dynamic_description()` | `false` | 描述是否随 turn 变化 |
| `should_list(ctx)` | `true` | 本 turn 是否进入模型可见的工具清单 |
| `execute(ctx, args)` | 包 `run` 成单 `Terminal` | 流式入口，**runtime 永远只调它** |
| `run(ctx, args)` | `Err(not_implemented)` | 阻塞便捷入口 |

`ListToolsContext`（`tool.rs:28` 引入）让 `description` / `should_list` 能按「当前查看器、附件、会话」做动态裁剪——这是「同一个工具在不同 turn 看到不同描述」的机制。

### 4.3 流构造器与不变量强制

两个受支持的构造器（`tool.rs:206` / `:218`）：

- `terminal_only(result)`：单条 `Terminal`，覆盖 99% 阻塞工具。
- `with_progress(progress, terminal)`：先排干 `progress` 流，再 await `terminal` 并发最后一条 `Terminal`。

不变量由约定 + `call_terminal` 兜底共同维护：流的 shape 必须是 `[Progress* , Terminal]`。违反 = 实现 bug，由 `dispatch.rs:64` 的 `stream_no_terminal` 错误暴露。

### 4.4 输出字节截断：`DEFAULT_TOOL_OUTPUT_BYTES`

`crates/codegen/xai-grok-tools/src/lib.rs:7`：

```rust
pub const DEFAULT_TOOL_OUTPUT_BYTES: usize = 40_000;
```

它在**工具清单生成**时被用来截断描述与 schema（`crates/codegen/xai-grok-tools/src/registry/types.rs:1168` 的 `interpolate_description` 与 `:1176` 的 `apply_to_schema`）：`truncation_config.interpolate_description(..., DEFAULT_TOOL_OUTPUT_BYTES, max_wait_block_ms())` 与 `truncation_config.apply_to_schema(...)`。含义：超大工具描述/入参 schema 会被裁剪到 40 KiB 量级，避免把整个上下文窗口喂给工具元数据。这是「工具清单可扩展但上下文不被撑爆」的关键旋钮。

### 4.5 搜索索引 `ToolSearchIndex`

`crates/common/xai-tool-runtime/src/search.rs:63`：

```rust
pub trait ToolSearchIndex: Send + Sync {
    fn search_snapshot(&self, query: &str, limit: usize) -> SearchSnapshot;
    fn list_server_summaries(&self) -> Vec<ServerSummary>;
}
```

- 后端无关：BM25 / OpenSearch / 内存线性都行，统一包成 `Arc<dyn ToolSearchIndex>`（`search.rs:77`）。
- `SearchSnapshot`（`search.rs:31`）同时返回 `results` + `total_hidden_tools` + `is_ready`，让调用方一次渲染「N / M 个结果」且能区分「索引还在预热」与「确实没有命中」。
- `ToolSearchResult`（`search.rs:11`）带 `tool_name / server_name / description / score / parameters / input_schema`——连 schema 一起给，调用方无需二次拉取即可构造调用。
- `ServerSummary`（`search.rs:42`）用于渲染「已连接集成」的系统提示（`name / description / tool_names`）。

用途：当工具总数远超上下文窗口时，runtime 用搜索索引做「按需召回」而非「全量清单」——这是 MCP/Hub 工具动辄上百个时的必需机制。

### 4.6 `CompoundResolver` 与多平面聚合

`crates/common/xai-computer-hub-core/src/resolver.rs:215`：

```rust
pub struct CompoundResolver { /* 聚合多个工具源，按 (url, principal) 维度 */ }
impl CompoundResolver { pub fn resolve(...) -> ResolvedTool { ... } }
```

`CompoundResolver` 把「内置 + MCP + Hub」等多路工具源聚合成一个统一的 `ToolDispatch`。它不直接实现 `ToolDispatch`，而是通过一个**绑定到单会话的弱引用适配器**：

- `InnerDispatchForResolver`（`crates/common/xai-computer-hub-core/src/inner.rs:34` / `:56`）持有 `Weak<CompoundResolver>` + `session_id`，并实现 `ToolDispatch`（`inner.rs:56`）。runtime 拿到的是 `Arc<dyn ToolDispatch>`，但路由逻辑全部委托给 `CompoundResolver::resolve`。
- `ResolvedTool`（`resolver.rs:34` 枚举）/ `ToolHandle`（`resolver.rs:80` trait）/ `ErasedTool<T>`（`resolver.rs:114` struct，导出见 `lib.rs:28`）是 `resolve` 的成果：一个「已定位到具体源 + 已绑定会话」的工具句柄。

这样设计的好处：**会话生命周期与工具源生命周期解耦**。会话销毁时 `Weak` 失效，不会把远程 Hub 连接拖死。

### 4.9 Computer Hub 平面（core + sdk）

- **core**：`crates/common/xai-computer-hub-core` 提供 `CompoundResolver`（4.6）与 `ResolvedTool`/`ToolHandle`。
- **sdk**：`crates/common/xai-computer-hub-sdk` 负责到 Hub server 的真实连接。核心是 `HubConnection`（`crates/common/xai-computer-hub-sdk/src/connection.rs`，每 `(url, principal)` 一个连接，多 `ToolServer` 共享，引用计数会话绑定，`crates/common/xai-computer-hub-sdk/src/connection.rs:5-12`）。它内置**断线重连 / 重放状态机**（`crates/common/xai-computer-hub-sdk/src/connection.rs:14-25`）：socket 掉线时，把 parked 的响应 waiter 全部以 `NetworkError` 快速失败（避免死锁），再以指数退避 + 全抖动重连，重跑 `hello` 握手，由 `ToolServer` 对每个活跃会话重放 `serve{session_id, tools}`。

这意味着远程工具服务器在临时断网后无需客户端重建会话状态，工具调用失败也能被 upper layer 捕获重试。

### 4.10 Hooks 平面（`xai-grok-hooks`）

生命周期钩子（PreToolUse / PostToolUse / Stop 等），而非「工具」本身，但常与工具调用联动：

- **注册表**：`HookRegistry`（`crates/codegen/xai-grok-hooks/src/discovery.rs:16`），`hooks_for(event)` / `has_enabled_hooks_for_canonical(event)` 按事件名取钩子；`registry_from_specs_deduped`（`discovery.rs:218`）做去重合并。
- **加载**：`load_hooks`（`discovery.rs:245`）与 `load_hooks_from_sources`（`discovery.rs:141`）从配置源（含 `HookOrigin` 区分来源，`config.rs:244`）收集 `HookSpec`（`config.rs:173`）。
- **执行**：`run_hook`（`crates/codegen/xai-grok-hooks/src/runner/mod.rs:163`）按 `RunContext`（`runner/mod.rs:17`）运行；`StopHookOutcome` / `StopOverride`（`result.rs:13` / `:21`）允许 Stop 钩子覆写模型「是否停下」的决定。

钩子是「在工具/会话边界插入用户脚本」的机制，独立于 `ToolDispatch`，但 `execute_tool_calls_batch` 在合适边界会触发它们（具体触发点见 11 章权限/沙箱一节）。

### 4.11 插件与技能平面（`xai-grok-plugin-marketplace` + `xai-grok-tools`）

- **插件市场**：`crates/codegen/xai-grok-plugin-marketplace` 提供 `installer.rs`（安装）、`catalog.rs`（目录）、`scanner.rs`（扫描本地插件）、`index.rs`（索引）。它是「外部能力以插件形式入驻」的通道。
- **技能（Skills）**：技能在工具层表现为一个可被模型调用的工具。核心类型：
  - `SkillManager`（`crates/codegen/xai-grok-tools/src/types/skill_discovery_tracker/mod.rs:85`）——技能发现的运行时管理，维护 `SkillListingSnapshot`（`mod.rs:45`）与 `SkillUpdateEffects`（`mod.rs:62`）。
  - `SkillTool`（`crates/codegen/xai-grok-tools/src/implementations/opencode/skill/mod.rs:77`）——把「调用一个技能」包装成 `Tool`，模型侧只是一个普通 `tool_use`。
  - `SkillDiscoveryReminder`（`crates/codegen/xai-grok-tools/src/reminders/skill_discovery.rs:45`）——在合适时机提醒模型「当前可用技能」。
  - `SkillInfo`（`crates/codegen/xai-grok-tools/src/implementations/skills/types.rs:41`）。
  - Shell 侧 RPC：`crates/codegen/xai-grok-shell/src/extensions/skills.rs` 提供 `SkillsAddRequest` / `SkillsListRequest` / `SkillsRemoveRequest` 等，通过 workspace RPC 增删查技能；`xai-grok-shell/src/remote/skills_client.rs:376` 的 `SkillsClient` 是远程客户端。
  - 遥测：`xai-grok-telemetry/src/events/mod.rs:1127-1151` 的 `SkillAdded` / `SkillRemoved` / `SkillDispatched` 记录技能生命周期。

一句话：**技能 = 被 `SkillManager` 发现、被 `SkillTool` 暴露、被 `SkillDiscoveryReminder` 提示、经 Shell RPC 增删的一组特殊工具**。

### 4.12 设计不变量小结（本章范围内）

1. **单一入口**：runtime 只调 `ToolDispatch::call`，所有平面（内置/MCP/Hub/技能）都收敛到它。
2. **单一边界**：泛型 ↔ JSON 的唯一转换发生在 `ToolDyn` blanket impl（`tool.rs:336`）。
3. **流不变量**：`[Progress* , Terminal]` 且 `Terminal` 恰好一个、永远最后。
4. **MCP 内容不变量**：`TypedToolOutput.model_output` 永非空（`tool.rs:238`）。
5. **上下文不变量**：工具清单描述/schema 受 `DEFAULT_TOOL_OUTPUT_BYTES = 40_000` 截断，防止上下文膨胀。
6. **版本不变量**：所有桥接对齐 `PROTOCOL_VERSION = "1.0.0"`（`handshake.rs:10`）。
