# 13 · 持久化、记忆与会话恢复

> **场景**：grok 关掉后，四样东西要能跨进程/跨会话存活——(1) **会话**：一次对话的完整状态（摘要 + 对话历史 + 事件流 + 各类状态文件），能被「恢复」「fork」「rewind」；(2) **恢复**：进程被重启/杀掉/崩溃后，下次加载能认出「上一轮 turn 没跑完」并把这件事补记下来，也能找回上一轮的进程级崩溃报告；(3) **检索**：在本机几百个会话里做全文搜索；(4) **记忆**：跨会话沉淀的知识（如「这个项目的构建命令是 X」）。
>
> **阅读说明**：源码基准 = 当前 HEAD `2178c69c`（2026-09-23，main）。**工具版本**：Rust 1.94.0（`rust-toolchain.toml:11`）；`ratatui 0.29 / tokio full / agent-client-protocol 0.10.4`；workspace members 共 **102** 个。
>
> 涉及 crate：`xai-chat-state`（会话状态的 actor + 持久化 trait）、`xai-grok-shell/src/session`（JSONL 存储实现 + 会话持久化 actor + fork/rewind + 中断轮次识别）、`xai-grok-memory`（跨会话记忆，**legacy 与 v2 两条互不相通的流水线**）、`xai-grok-session-events`（`events.jsonl`）、`xai-sqlite-journal`（SQLite journal 模式选择）、`xai-grok-session-search`（SQLite FTS5 全文索引）、`xai-grok-foreign-sessions`（Claude/Codex/Cursor 会话只读扫描）、`xai-grok-active-sessions`（TUI 活跃会话注册表）。

## 第二层 · 一个完整例子（全路径走读）

以「用户上次会话崩了，今天重新打开 grok，想找回那个会话并让模型记得项目约定」为例：

```
① 进程启动（crates/codegen/xai-grok-pager-bin/src/main.rs）
   xai_crash_handler::install_terminal_restore_only()
   crash_dir = crash_dir_for(&args)     ← leader 模式是 crash/leader
   xai_crash_handler::check_previous_crash(&crash_dir)   lib.rs
     → 有 last-crash.bin 则符号化 + 写 last-crash-report.txt + 归档 history/
   注意：本版**没有**启动期"扫孤儿会话"这一步；
         active_sessions.json 的清理推迟到下一次 register（见 ③）
        │
② 用户从列表点开那个会话 → 从磁盘加载：
   JsonlStorageAdapter::load_session(..)（实现 StorageAdapter）
     读 summary.json（标题/模型/head_commit/head_branch/request_id/next_trace_turn/…）
     读 chat_history.jsonl（CHAT_FORMAT_VERSION = 1，persistence.rs）
     读 updates.jsonl（SessionUpdateEnvelope 逐行，含 timestamp）
     读 plan.json / plan_mode_state.json / signals.json / goal_mode_state.json
     rewind_points.jsonl 走惰性加载（FileStateTracker），不在 resume 热路径上
        │
③ 加载时检查「上一进程有没有把 turn 跑完」：
   调用方：MvpAgent::record_interrupted_turn（mvp_agent/session_setup.rs）
   被调用方：detect_interrupted_turn(session_dir, summary)
              interrupted_turn.rs
     读 summary.request_id / summary.next_trace_turn（checked_sub(1)）
     扫 events.jsonl 末尾 256 KiB，找最后一条 turn_started/turn_ended
     若最后是 turn_started → 返回 InterruptedTurn{trace_turn, prompt_id, started_at}
   命中后 record_interrupted_turn 做三件事：
     persistence.append_update_durably(turn.turn_completed_update(session_id))
       → 往 updates.jsonl 补一条 turn_completed，让前端画出结束标记
     turn.close_events_turn(session_dir)
       → 往 events.jsonl 补 TurnEnded{outcome: Interrupted}
   随后 MvpAgent::finish_interrupted_turn 再把模型提醒与 trace 结果补齐：
     SessionCommand::NoteInterruptedTurn{turn} → session.push_system_reminder(..)
     turn.turn_result()（completed:false, stop_reason:"interrupted"）
       → upload::turn::spawn_upload_task("interrupted_turn_result", ..)
        │
④ 会话恢复后，模型要回答「这个项目怎么构建」：
   记忆系统先召回跨会话知识：
   MemoryMode::Legacy → 读 {workspace_hash}/MEMORY.md（项目级）
                        + ~/.grok/memory/MEMORY.md（全局级）
   MemoryMode::V2     → 读 {scope}/topics/*.md + 生成的 MEMORY.md 清单
        │
⑤ 若记忆里没有，模型这轮产出的「构建约定」会被写回记忆：
   legacy: embed_missing_chunks(index, provider)  lib.rs
           （分批 32 条补向量嵌入，支撑语义检索）
   v2:     capture → observation inbox → Dream/consolidation → topics
           （见 v2_capture.rs / v2_consolidation.rs / dream.rs）
        │
⑥ 用户想翻「上周那次讨论 OAuth 的会话」：
   session_search::execute_search(manager, root, &req)  manager.rs
     → 等首次 bootstrap 最多 BOOTSTRAP_WAIT_TIMEOUT
     → SQLite FTS5 BM25 查询 sessions/session_search.sqlite
     命中后按 cwd 解析出真实会话目录再打开
        │
⑦ 会话跑到一半崩溃（SIGSEGV）：
   xai-crash-handler 的 sigaction 处理器写 crash/last-crash.bin（含 signal/si_code/栈）
   active_sessions.json 里的条目因为没走到 try_unregister 而留下
   → 下次启动是 ① 的进程级回读；下次 register 顺手把死 PID 剪掉（见第三层步骤 7）
```

链路说明：**会话是「单次、可恢复、可 fork/rewind、可搜索」；恢复分两层（进程级 crash blob + 会话级「未闭合 turn」与活跃会话注册表）；记忆是「长期、跨会话、按工作区」**。三者都落在 `~/.grok/` 下不同子目录，互不干扰。

## 第三层 · 详细逐步说明（主链路拆解）

### 步骤 1 — 会话状态 actor 与持久化 trait（`xai-chat-state`）

`crates/codegen/xai-chat-state/src/lib.rs · Module：xai-chat-state` 的 crate doc 给出架构图：`SessionActor` 用 Command 与 `ChatStateActor` 通信，后者跑在专用 tokio 任务里，内部 `State` **无需锁**（`conversation: Vec<ConversationItem>`、`sampling_config`、`prompt_index`、`total_tokens`），事件经 `event_tx` 回推 `Session`。crate doc 还点名它「从 `xai-grok-shell` 的 `acp_session.rs` 抽出来，沿用与 `xai-hunk-tracker` 相同的 actor 模式」。

`trait ChatPersistence: Send + 'static`（`crates/codegen/xai-chat-state/src/persistence.rs · ChatPersistence`）是持久化的**唯一入口**，五个方法：

| 方法 | 语义 | 是否有 ack |
|------|------|-----------|
| `persist_message(&mut self, item: &ConversationItem)` | 追加单条到 `chat_history.jsonl` | 无（fire-and-forget） |
| `persist_working_directory_switch_and_ack(&mut self, item)` | 持久化一次 cwd 切换「代（generation）」 | 有（`oneshot<Result<StrictAppendAck, StrictAppendError>>`） |
| `replace_history(&mut self, items: &[ConversationItem])` | 整体替换历史（压缩 / rewind） | 无 |
| `replace_history_for_strip_and_ack(&mut self, items)` | **破坏性**的图片剥离重写：先备份磁盘历史再替换 | 有（`oneshot<io::Result<()>>`） |
| `flush(&mut self)` | 冲刷待写 | 无 |

注释把设计约束写死：「actor **独占** `Box<dyn ChatPersistence>`，所以 trait 方法取 `&mut self` —— 无锁、无原子、无共享状态。真实实现包着一个 actor 独占的 sender。」`replace_history_for_strip_and_ack` 的注释补了一条安全约束：**备份失败会 gate 掉重写**，这样「可恢复性」不会悄悄蒸发。

`enum StripOutcome`（`persistence.rs · Enum：StripOutcome`）把剥离结果分成四态，注释点出动机：「类型化，这样一个死掉的 actor 绝不可能伪装成『什么都没剥离』」：

- `Applied { stripped: usize }` —— 已剥离且持久化（同一 URL 存两次算两次）；
- `NoMatch` —— 没有存量图片匹配请求的 URL；
- `WriteFailed { stripped: usize }` —— 内存已剥离但备份或落盘失败，**按未持久化处理**（下次加载会被重新污染）；
- `ActorUnavailable` —— chat-state actor 已死，剥离可能根本没发生。

同文件还有两个测试替身：`MockChatPersistence`（用 `mpsc::UnboundedSender<PersistenceRecord>` 把每次调用报告给测试；`new_failing_strip_writes` 专门钉「诚实失败」那一半契约；`new_with_manual_persistence_ack` 让 ack 由测试掌控）与 `NullChatPersistence`（全丢，给 benchmark / noop 场景）。`enum PersistenceRecord`（`persistence.rs · Enum：PersistenceRecord`）是记录类型：`Message` / `AcknowledgedMessage` / `ReplaceHistory` / `ReplaceHistoryForStrip` / `Flush`。

`ChatStateCommand`（`crates/codegen/xai-chat-state/src/commands.rs · Enum：ChatStateCommand`）本版有一处签名变化：`RepairDanglingAfterHarnessHalt { class, answers }` 多了 `answers: HashMap<String, String>`，语义是「只为仍然悬空的 tool call id 写答案，其余丢弃」；对应的 handle 方法 `ChatStateHandle::repair_dangling_after_harness_halt(class, answers)` 同步加参。另有新模块 `compaction_image_context`（`crates/codegen/xai-chat-state/src/compaction_image_context.rs`）承接压缩期的图片上下文，属于压缩链路，不影响本章的持久化契约。

### 步骤 2 — 生产实现：通道适配 + 单一写入 actor

`crates/codegen/xai-grok-shell/src/session/chat_persistence.rs · ChannelChatPersistence` 是 `ChatPersistence` 的生产实现——**它只做一件事：把调用翻译成 `PersistenceMsg` 发到 session 持久化 actor 的 channel**：

```
ChatPersistence::persist_message            → PersistenceMsg::Chat(item)
ChatPersistence::persist_working_directory_switch_and_ack
                                            → PersistenceMsg::AppendCwdSwitchAndAck{item, respond_to}
ChatPersistence::replace_history            → PersistenceMsg::ReplaceChatHistory(items)
ChatPersistence::replace_history_for_strip_and_ack
                                            → PersistenceMsg::ReplaceChatHistoryForStripAndAck{messages, respond_to}
ChatPersistence::flush                      → PersistenceMsg::Flush
```

两个 ack 路径都有一个「channel 已关」的兜底分支：**发不出去也必须 ack 一个错误**，而不是挂住或假成功——`channel_persistence_acks_strip_error_when_actor_gone` 单测专门钉这条。

`crates/codegen/xai-grok-shell/src/session/persistence.rs` 的模块 doc 给出了这个 actor 的**硬掉电丢失契约**，这是本章最值得记住的一段：

- 即发即忘的写（流式 chunk、turn 中段的工具记录、feedback / btw_history 追加）是**缓冲**的：自上一个屏障以来的任何内容都可能丢，但丢失范围被限制在「正在跑的这轮 turn 的尾部」。
- 任何调用方 **await** 的写（`FlushAndAck`、`AppendUpdateDurablyAndAck`、`AppendCwdSwitchAndAck`）在 ack 触发时**已在稳定介质上**。屏障只 sync 自上一个屏障以来变脏的文件。一个失败的缓冲写（chat 追加、流式 update…）会**latch（闩住）**到下一个屏障，届时屏障返回该错误，而不是去 sync 陈旧或缺失的字节然后 ack 成功。
- 原子 rename 写会在 rename 前 fsync 临时文件，所以替换文件得到的是旧内容或新内容，**绝不会是垃圾**。若是「创建」，还会额外 sync 所在目录；会话目录创建会 sync 新建链条经过的每一级目录。所以首次创建（一个会话的第一个 `summary.json` 及其所在会话目录）在写返回时就是持久的。Windows 没有目录 fsync，那里 NTFS 元数据日志可能把一次极新的创建回滚成「不存在」，但**不会回滚成垃圾**。

`enum PersistenceMsg`（`persistence.rs · Enum：PersistenceMsg`）是一个大枚举，实测变体覆盖：`Update` / `AppendUpdateDurablyAndAck` / `Chat` / `AppendCwdSwitchAndAck` / `ReplaceChatHistory` / `ReplaceChatHistoryForStripAndAck` / `Flush` / `FlushAndAck` / `ProbeWritable` / `UpgradeToWriteback{auth_manager}` / `StampSessionIdentity` / `SetRemoteAgentId` / `CurrentModel` / `PlanState` / `PlanModeState` / `GoalModeState` / `DeleteGoalModeState` / `WorkflowRunState` / `WorkflowRunStateAndAck` / `DeleteWorkflowRunState` / `ContentChunk` / `GeneratedTitle` / `RegenerateTitle` / `LastRecap` / `ManualTitleRenamed` / `ResetTitleToAuto` / `LastTurnSummary` / `RewindPoint` / `TruncateRewindPoints{from_index}` / `MergeRewindPointsFrom{target_index}` / `CollectionId` / `NextTraceTurn` / `WakeStart` / `WakeAbort{prior, respond_to}` / `HoldForTest` / `Signals` / `UsageTurn{turn_number, live}`。**所有会话文件写都走这一条 FIFO**——这是「同一会话不会有两个写者互相打架」的机制保障。

三个冲刷层级：`flush_pending`（写缓冲区 → 文件）、`flush_and_sync`（再 fsync 变脏文件）、`flush_and_sync_all`（全部）。

### 步骤 3 — JSONL 落盘层（`StorageAdapter` + `JsonlStorageAdapter`）

`crates/codegen/xai-grok-shell/src/session/storage/mod.rs` 的文件常量（`pub(crate) const`）：`SUMMARY_FILE = "summary.json"`、`PLAN_FILE = "plan.json"`、`CHAT_HISTORY_FILE = "chat_history.jsonl"`、`UPDATES_FILE = "updates.jsonl"`。

`trait StorageAdapter: Send + Sync`（`storage/mod.rs · StorageAdapter`）是存储后端的抽象（注释：「Abstracts over different storage backends (JSONL, SQLite, etc.)」）。除 `init_session` 外，方法可粗分为四组：

**「commit-aware」这一族方法的语义**值得单独说：它们区分「JSONL 记录已提交」与「记账失败」，因为这两件事的恢复策略完全不同——记录没提交可以安全重放，记账失败则不能重复追加。

**追加的持久化核心**是 `append_jsonl_line_sync_with`（`storage/jsonl/mod.rs · append_jsonl_line_sync_with`），这段代码把「JSONL 追加」的所有边界情况都处理了：

```rust
fn append_jsonl_line_sync_with(
    path: &Path,
    mut line: Vec<u8>,
    durability: AppendDurability,
    mut sync_file: impl FnMut(&std::fs::File) -> io::Result<()>,
    mut sync_parent: impl FnMut() -> io::Result<()>,
) -> Result<(), AppendLineError> {
    debug_assert!(line.ends_with(b"\n"), "JSONL record must end with \\n");
    let lock = Self::lock_append(path).map_err(AppendLineError::NotCommitted)?;
    let result = (|| {
        let mut file = OpenOptions::new().read(true).create(true).append(true)
            .open(path).map_err(AppendLineError::NotCommitted)?;
        let len = file.metadata().map_err(AppendLineError::NotCommitted)?.len();
        if len > 0 {
            file.seek(io::SeekFrom::Start(len - 1)).map_err(AppendLineError::NotCommitted)?;
            let mut last = [0u8; 1];
            file.read_exact(&mut last).map_err(AppendLineError::NotCommitted)?;
            if last[0] != b'\n' {
                tracing::warn!(path = %path.display(),
                    "jsonl file has a torn trailing line (previous append crashed mid-write?); \
                     terminating it before appending");
                line.insert(0, b'\n');
            }
        }
        file.write_all(&line).map_err(AppendLineError::NotCommitted)?;
        file.flush().map_err(AppendLineError::Committed)?;
        if matches!(durability, AppendDurability::Durable) {
            sync_file(&file).map_err(AppendLineError::Committed)?;
            drop(file);
            sync_parent().map_err(AppendLineError::Committed)?;
        } else { drop(file); }
        Ok(())
    })();
    let _ = lock.unlock();
    result
}
```

四个要点：(1) 全程持 `fs2` 建议性文件锁（`lock_append`），**同会话并发写被串行化**；(2) **torn-line 自愈**——如果上一次追加在写一半时崩溃，文件最后一个字节不是 `\n`，这里会在新记录前补一个 `\n`，把残行终止掉，于是后续解析不会把两条记录粘成一条；(3) 错误分两级：`AppendLineError::NotCommitted`（write_all 之前失败）与 `Committed`（write_all 之后失败，此时记录至少进了 page cache）；(4) `AppendDurability::{Buffered, Durable}` 控制是否做 `sync_file` + `sync_parent`。

围绕它的周边：`append_jsonl`（默认 `Buffered`）、`append_jsonl_with_durability`、`append_jsonl_line_blocking`、`sync_file_path_durable`、`append_jsonl_line_sync`、`sync_file_durable`、`sync_parent_directory`、`lock_append`、`sync_parent_if_first_create_summary`（**只在首次创建 `summary.json` 时 sync 父目录**）、`write_summary_sync`、`read_summary_sync`、`read_chat_history_sync` / `read_chat_history_sync_bounded`。

`JsonlStorageAdapter` 的测试用「探针（probe）」模式注入失败：`with_update_append_probe`、`with_probes`、`with_file_sync_probe`、`with_parent_sync_probe`——让测试能精确地在「append 之后」「file sync 之后」「parent sync 之后」各点注入 I/O 错误，从而验证前面的丢失契约。这些探针字段全部 `#[cfg(test)]`，生产构建里不存在。

`crates/codegen/xai-grok-shell/src/session/fork.rs` 的模块 doc 说得很清楚：「Forks a saved session to a new working directory with a new session ID. This creates new session files but **does not start the session**.」

```

2. 组 source_info / target_info（Info { id, cwd }）
3. new_session_id = request 指定 或 generate_fork_session_id(源 id)
```

### 步骤 7 — 恢复：三层

**第一层：未闭合的 turn（`xai-grok-shell/src/session/interrupted_turn.rs`）**。这是本版**新增**的会话级恢复机制，模块 doc 一句话：「Records, at session load, a turn the previous process never finished so it does not look like a silent stop.」

- `Const：INTERRUPTED_STOP_REASON = "interrupted"`（与 `error` / `cancelled` 区分，让 trace 消费者能分辨）。
- `Const：INTERRUPTED_MESSAGE`（转录行与 `turn_result.error` 的文案：「Grok stopped before this turn finished (the agent process exited or was restarted). Committed tool results were kept.」）。
- `Const：EVENTS_TAIL_BYTES = 256 * 1024`——只扫 `events.jsonl` 尾部，注释说「一轮的事件在这个预算里放得下很多遍」。
- `Struct：InterruptedTurn { trace_turn: u64, prompt_id: String, started_at: Option<String> }`。

**第二层：活跃会话注册表（`xai-grok-active-sessions`）**。crate doc（`crates/codegen/xai-grok-active-sessions/src/lib.rs · Module：xai-grok-active-sessions`）：「Tracks open TUI sessions in `~/.grok/active_sessions.json`. A clean exit removes the entry, a crash leaves it behind, and the next `register` prunes entries whose PID is dead.」

- `Struct：ActiveSession { session_id: acp::SessionId, pid: u32, cwd: String, opened_at: DateTime<Utc> }`。
- 三个文件名常量：`DATA_FILENAME = "active_sessions.json"`、`LOCK_FILENAME = "active_sessions.lock"`、`TMP_FILENAME = "active_sessions.json.tmp"`。
- **本版新增的有界锁**：`Const：LOCK_ACQUIRE_TIMEOUT = 2s`、`Const：LOCK_POLL_INTERVAL = 50ms`，注释给出理由——「在 NFS home 上 `flock` 是网络锁管理器锁、没有租约：持有者在对的时刻被杀就永久搁浅，所以绝不无限等待。活着的持有者只做一次小的读-改-写，因此锁被持有这么久就是搁浅了」。
- 公共 API 默认落到 `xai_grok_config::grok_home()`：`register(session)`（按 `session_id` 幂等，**并剪掉 PID 已死的条目**；锁仍被持有超过 `LOCK_ACQUIRE_TIMEOUT` 时返回 `io::ErrorKind::TimedOut`）、`try_unregister(session_id) -> io::Result<bool>`（**信号处理器用的非阻塞版本**；锁竞争时返回 `Ok(false)`，注释：「孤儿会在下次 `register` 被剪掉」）。可注入 root 的 `_in` 变体：`register_in`、`try_unregister_in`、`list_in`。
- `register_in` 的语义全在那一行 `retain` 里：

```rust
pub fn register_in(root: &Path, session: ActiveSession) -> io::Result<()> {
    with_locked_state(root, LOCK_ACQUIRE_TIMEOUT, |sessions| {
        sessions.retain(|s| s.session_id != session.session_id && is_pid_alive(s.pid));
        sessions.push(session);
    })
}
```

- `try_unregister_in` 用 `with_locked_state(root, Duration::ZERO, ..)` 拿锁（零超时 = 只试一次），把 `TimedOut` 映射成 `Ok(false)`。
- `with_locked_state(root, timeout, mutate)`（`lib.rs · with_locked_state`）是加锁的读-改-写：建目录 → `open_lock_file` → 轮询 `lock_file.try_lock()` 直到成功或超时 → 读 `read_data_file` → `mutate` → `write_data_file_atomic`。注释点明「**关闭文件即释放锁，所以每条返回路径都靠 drop 解锁**」，因此没有显式 `unlock`。`TryLockError::WouldBlock` 继续轮询，`TryLockError::Error(e)` 直接返回。
- 原子写：`write_data_file_atomic(tmp_path, data_path, sessions)`——`serde_json::to_string_pretty` → 写 tmp → `fs::rename(tmp, data)`，rename 失败时清掉 tmp。
- 损坏容错：`read_data_file`——文件为空返回空 `Vec`；JSON 解析失败**只 warn 并返回空列表**（「active_sessions.json is corrupted, starting with empty list」），不让损坏的注册表阻塞启动；`NotFound` 也返回空。
- **PID 存活判定**：`is_pid_alive(pid)`——Unix 先 `i32::try_from(pid)` 且要求 `> 0`（否则直接判死），再用 `libc::kill(pid, 0)`，`ret == 0` 为存活，**`EPERM` 也算存活**（进程存在但不属于我们）；Windows 用 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` 能打开即存活（并 `CloseHandle`）；其它平台保守地**假定存活**。

单测钉了五条：`register_is_idempotent`、`concurrent_registers_no_corruption`（10 个线程并发注册后正好 10 条）、`try_unregister_skips_if_locked`、`locked_update_times_out_when_lock_stays_held`（50ms 预算 + 外部持锁 → `TimedOut`，且数据未被改动）、`locked_update_retries_until_holder_releases`（持有者 100ms 后释放 → 注册成功）、`corrupt_file_recovers`。

调用方（`Grep` 已核）：`crates/codegen/xai-grok-pager/src/app/effects/mod.rs` 的 `Effect::RegisterActiveSession` → `xai_grok_active_sessions::register(..)`；`crates/codegen/xai-grok-pager/src/app/effects/helpers.rs` 的 `unregister_active_session_best_effort` → `try_unregister_in(..)`；`crates/codegen/xai-grok-pager/src/app/signal_handler.rs` → `try_unregister(sid)`；`crates/codegen/xai-grok-pager/src/headless.rs` 也走 `register` / `try_unregister`。**当前 HEAD 没有任何调用方读回注册表来做「崩溃会话提示」**——本版不存在 `collect_crashed`，也没有等价的启动扫描。

**第三层：进程级崩溃报告（`xai-crash-handler`）**。会话级条目只能告诉你「有个会话没干净退出」；如果进程是 SIGSEGV/SIGBUS 挂的，还会有第二份证据。crate doc（`crates/codegen/xai-crash-handler/src/lib.rs`）说明：Unix 用 `sigaction(2)` 捕 SIGBUS/SIGSEGV/SIGABRT（**捕 SIGABRT 意味着 `panic = "abort"` 构建——所有发行版——在 Rust panic 时也能留下报告**），Windows 走 `SetUnhandledExceptionFilter`。

回读侧 `check_previous_crash(crash_dir) -> Option<CrashReport>`（`lib.rs · check_previous_crash`）：读 `crash_dir/last-crash.bin` → `format::CrashBlob::parse` → `symbolicate::resolve_frames` → `symbolicate::format_report` → `write_owner_only(last-crash-report.txt)` → `archive_report`（写 `history/crash-{timestamp}.txt` 并只保留最近 `MAX_HISTORY = 5` 份）→ 删除二进制 blob 防重复处理。`write_owner_only` 在 Unix 上先 `OpenOptions::mode(0o600)` 创建，**再显式 `set_permissions(0o600)` 后写**——注释解释：`mode()` 只在创建时生效，预先存在的 0644 文件会在写入期间保持 world-readable；单测钉了「新建即 0600」与「覆盖既有 0644 必须收紧」两条。`Struct：CrashReport` 暴露 `signal_name` / `si_code` / `faulting_address` / `timestamp` / `app_version` / `backtrace` / `report_path`。

`crates/codegen/xai-grok-pager-bin/src/main.rs` 里的顺序是硬约束（crate doc 明说 `check_previous_crash` 必须在 `install` 之前，因为 `install` 用 `O_TRUNC` 打开 `last-crash.bin`）：`install_terminal_restore_only()` → `check_previous_crash(&crash_dir)` → `install(CrashHandlerConfig { app_version, crash_dir })`。其中 `crash_dir = crash_dir_for(&args)`（`main.rs · crash_dir_for`）：leader 模式返回 `{grok_home}/crash/leader`，否则 `{grok_home}/crash`——注释解释原因：pager 与 leader 共用一个目录会各自在启动时抹掉对方尚未处理的崩溃 blob。

### 步骤 8 — 会话检索（`xai-grok-session-search`）

crate doc（`crates/codegen/xai-grok-session-search/src/lib.rs`）给了完整分层与两条硬契约。**分层自底向上**：

- `fts` —— 拥有 schema、BM25 查询、以及带 fence 的 `meta` 写入；`SessionSearchIndex`（`fts.rs · SessionSearchIndex`）、`with_index`、`SessionDoc`、`SessionSearchRow`、`QueryResult`、`is_session_id_like(query)`（**私有**，`fts.rs · is_session_id_like`）。
- `recovery` + `db` —— `recovery` 把不可用的库文件分类、隔离（quarantine）、重建空库（`message_indicates_unusable_db`、`with_suffix`）；`db` 在其上加「打开 + 重试」的 plumbing。
- `doc` —— 把「会话 + 抽取文本」转成索引文档。
- `bootstrap` —— 跨进程、带租约（lease）保护的**全量重建索引**。
- `manager` —— 对每个会话的 upsert 去抖（debounce），并应答查询。

**两条硬契约**：① 「该 crate **从不直接读会话存储**：调用方注入 `SessionSource` 与 `ContentExtractor`」——这样 `updates.jsonl` 的线格式归存储层所有，不在这里重复一份；② 索引是**可重建的 SQLite FTS5 缓存**，位于 `<grok home>/sessions/session_search.sqlite`。

`source.rs` 就是那对注入点：`struct IndexableSession`、`trait SessionSource`、`type SessionSourceFactory = fn(PathBuf) -> Box<dyn SessionSource>`、`type ContentExtractor = fn(&Path) -> io::Result<(String, u64)>`。

`manager.rs` 的 `SearchIndexManager` 的构造契约写在 doc 上：「管理本进程接触过的**每一个** grok home 的后台会话索引；构造时要求有活跃 tokio runtime（会 spawn 任务）。」`start(source_factory, extract)` 起一个 dispatcher 任务，处理两类命令：`Enqueue{root, job}` → `dispatch`；`BootstrapOnce{root}` → 若该 root 首次则派 `SearchIndexJob::BootstrapAll`，否则派 `SearchIndexJob::RecheckBootstrap`（注释：「DB 是共享的：重新核验磁盘上的 marker，排在仍在跑的同 worker `BootstrapAll` 之后」）。`dispatch` 按 root 懒建 worker 任务（`state.workers.entry(root).or_insert_with(...)`）。公共面：`bootstrap_once(root)`（幂等，且**急切地**把 `bootstrapping` 置位，好让轮询者在后台任务启动前就看到 `true`）、`status()`（返回 `SearchIndexStatus { bootstrapping, indexed, total, skipped, unchanged }`）、`enqueue(root, session_id, cwd)`。`execute_search(manager, root_dir, req)`（`manager.rs · execute_search`）带 `#[tracing::instrument(name = "session_search.query", skip_all)]`，注释：「等首次 bootstrap 最多 `BOOTSTRAP_WAIT_TIMEOUT`，这样查询跑在已填充的索引上」。worker 内部：`run_worker`、`handle_job`、`flush_ready`（**去抖后批量落盘**）、`upsert_by_key`、`upsert_session`、`delete_session`、`evict_session`。

**跨进程 lease**（`bootstrap.rs` doc）：「索引自己的 `meta` 表里放一个 lease claim，让一个进程跑 `reindex_all`，等待者采纳它已完成的 bootstrap marker。」可调参数：

| 常量 | 值 | 语义 |
|------|-----|------|
| `BOOTSTRAP_MAX_CONCURRENT` | 4 | 并发会话索引数 |
| `BOOTSTRAP_PER_SESSION_TIMEOUT` | 30s | 单会话索引超时 |
| `BOOTSTRAP_MAX_FILE_SIZE` | 30 MiB | 超此大小跳过 |
| `TIMING.lease` | 300s | claim 超过此时长即视为被放弃，可被接管 |
| `TIMING.refresh` | 30s | 持有者刷新 claim 的周期 |
| `TIMING.peer_wait` | 60s | 等待者最多等同伴多久 |
| `TIMING.poll` | 1s | 等待者轮询间隔 |

并且有两处编译期 `assert!`：「refresh 必须在 lease 内触发多次；waiter 必须在 peer wait 内至少轮询一次」（`try_bootstrap_with_lease` 会故意把 peer wait 置零：只尝试一次 claim，不等待循环）。

进度状态用一个 `AtomicU64` 打包（`BootstrapProgress`）：「bit 0 是 `bootstrapping` 标志，高位存一个每次 set 都自增的 generation。两者共享一个原子量，这样一个 compare-exchange 只有在没有更新的 set（一次 heal 重入队、一次并发查询）时才会清标志。」配 `begin_bootstrapping()` 返回 generation、`end_bootstrapping(generation)` 只在 generation 匹配时才清。`BootstrappingGuard` 的 `Drop` 保证「**包括 unwind 在内**的每条退出路径都清标志，除非更新的 `begin_bootstrapping` 已经接手」。其余：`bootstrap_with_lease_inner`、`claim_bootstrap_lease`、`ClaimToken`、`spawn_claim_refresher`（配 `RefresherGuard`）、`release_bootstrap_claim`、`write_last_bootstrap_at_if_claim_owner`、`has_bootstrap_claim`、`clear_last_bootstrap_at`、`SharedIndex`、`reindex_all`。meta 表键是 `Const：META_KEY_BOOTSTRAP_CLAIM = "bootstrap_claimed_at"` 与 `Const：META_KEY_LAST_BOOTSTRAP = "last_bootstrap_at"`（`fts.rs`）。

### 步骤 9 — SQLite journal 模式选择（`xai-sqlite-journal`）

这个 crate 存在的唯一理由是**网络文件系统上的 SIGBUS 隐患**。crate doc（`crates/codegen/xai-sqlite-journal/src/lib.rs`）把因果链写全了：WAL 把 wal-index 放在 mmap 的 `-shm` 文件里，依赖一致共享内存 + 可靠的 POSIX 锁——这两样网络文件系统都不保证。当 `$HOME`（从而 `~/.grok`）是 NFS 挂载且被多台机器同时使用，同伴主机在 WAL 恢复或关闭期间截断/重建 `-shm`，会把我们映射的底层抽掉，下一次 wal-index 读就死于 SIGBUS。在这种挂载上改用 rollback journal（SQLite 官方文档就写了「WAL 不适用于网络文件系统」），并且**每台主机打开自己的 per-host DB 文件**（见 `effective_db_path`），这样任何同伴——包括那些会把它翻回 WAL 的修复前二进制——都不会共享该文件。

- `enum JournalMode { Wal, Truncate }`，注释解释了为什么 Truncate 而不是 DELETE：「提交时截断（而非 unlink）——在网络文件系统上安全，且比 DELETE 模式便宜：没有每次提交的 create/unlink 命名空间往返，也没有 NFS 的 `.nfsXXXX` silly-rename 垃圾。」
- `JournalMode::for_db_path(db_path)`（`lib.rs · JournalMode::for_db_path`）——`GROK_SQLITE_JOURNAL_MODE`（`wal`|`truncate`）可强制覆盖，作为现场 kill-switch；强制时 `tracing::info!` 记 `source = "env"`（注释：「让现场切换 kill-switch 在日志里可 grep」）；取值非法时 `tracing::warn!` 记非法值并回落到探测（「紧急 kill-switch 打错字必须响亮，不能静默忽略」）；否则按 `is_network_fs(parent_dir)` 选 Truncate 或 Wal，并记 `source = "statfs"` 的 debug 日志。注意它分类的是**父目录**（DB 文件本身可能还不存在），所以调用方必须先建目录。
- `JournalMode::effective_db_path(db_path)`（`lib.rs · JournalMode::effective_db_path`）——只有 Truncate 才改路径：插到最后一个扩展名前（`worktrees.db` → `worktrees.h-<host>.db`），无扩展名就追加；对已带 `-h-` 标签的路径幂等；拿不到 hostname 就退回原路径（仍是 TRUNCATE）。
- `JournalMode::open(db_path)`（`lib.rs · JournalMode::open`）——在 `effective_db_path` 上打开读写连接并 `apply_with_retry`。另有只读面 `open_readonly(db_path)` 与 `open_readonly_until(db_path, deadline)`（默认 deadline = `Instant::now() + BUSY_RETRY_BUDGET`）。
- 超时常量：`Const：BUSY_TIMEOUT = 5000ms`（注释：「等同伴的锁，而不是立刻失败；与所有消费方历史上的设置一致」）、`Const：BUSY_RETRY_BUDGET = 10s`（注释：「一个预算用于熬过 `SQLITE_BUSY`。内层重试共享调用方的 deadline，这样两个计时器不会叠加成两倍宣称等待」）。

`xai-grok-memory` 的 v2 流水线也直接用这个 crate（`v2.rs` 里 `use xai_sqlite_journal::JournalMode;`），并且对网络文件系统**直接拒绝**：`V2StorageError::UnsupportedNetworkFilesystem`（`crates/codegen/xai-grok-memory/src/v2.rs · V2StorageError`）的报文是「v2 memory scope … is on a network filesystem; memory-v2 requires local shared-memory coordination」。

### 步骤 10 — 跨会话记忆（`xai-grok-memory`）

crate doc（`crates/codegen/xai-grok-memory/src/lib.rs · Module：xai-grok-memory`）第一条就是：「**两条隔离的流水线。它们不共享文件、搜索、flush 或 Dream。** 改动任一条之前先看 crate 的 `AGENTS.md`。」**本版该 crate 未发生变化，这条结构结论仍然成立。**

| | legacy | v2 |
|---|--------|-----|
| 根目录 | `~/.grok/memory/` | `~/.grok/memory-v2/` |
| 形态 | markdown 树 | topics + observation inbox + 生成的 `MEMORY.md` |
| 参考实现 | `storage.rs`（2053 行） | `v2.rs`（1021 行） |
| 互操作 | — | **v2 永不读写 legacy 树** |

legacy 布局（crate doc 原文）：

```text
~/.grok/memory/
  ├── MEMORY.md                         # Global curated knowledge
  └── {workspace_hash}/                 # Per-workspace (blake3(cwd)[..16])
      ├── MEMORY.md                     # Project-level curated knowledge
      └── sessions/
          └── YYYY-MM-DD-{slug}-{sid8}.md  # Session logs
```

即：工作区分桶键是 `blake3(cwd)` 的前 16 个字符（与 06 章路径系统的 blake3 编码同源）；两层 `MEMORY.md` 让「个人通识」与「项目约定」分离；会话日志按「日期-slug-会话 id 前 8 位」归档。

**开关与模式**（crate doc）：「通过 `MemoryConfig::resolve_settings` 解析启用状态。`GROK_MEMORY`、`[memory] enabled`、`[memory_v2] enabled` 都参与。关闭时宿主不初始化该 crate。」具体类型在 `crates/codegen/xai-grok-config-types/src/memory.rs`：

- `enum MemoryMode { Legacy, V2 }`，doc 强调「模式与其余 `MemoryConfig` 一起**解析一次**，对已在跑的会话不再改变」；`Legacy` 是 `#[default]`。
- `enum MemoryV2Rollout { Off, RecordOnly, Shadow, Active }`（`Active` 为默认）——四态的语义由三个谓词定义：`allows_capture()`（`!= Off`）、`exposes_memory()`（`== Active`）、`commits_topics()`（`== Active`）；`restrict(other)` 取更保守的一个，因此多处 rollout 设置可以「取最严」地合并。
- `struct MemorySettings`——raw `[memory]` 表，字段含 `enabled` / `index` / `embedding` / `search` / `initial_injection` / `session` / `watcher` / `gc` / `dream`；注释「缺失被保留以支持逐字段回落」。
- `struct MemoryV2Settings`——raw `[memory_v2]` 表：`enabled`、`capture_status_enabled`（只给 UI 的调试通知；遥测与 tracing 永远记录）、`rollout`、`capture_enabled`、`automatic_dream_enabled`、`manual_dream_enabled`、`file_writes_enabled`、`archived_retention_days`、`job_retention_days`。
- `MemoryConfig::resolve_settings(..)` 里有一条交叉规则（注释）：`[memory] enabled = false` 会关掉 legacy，**除非**同一份 TOML 里设了 `[memory_v2] enabled = true`；v2 有独立的 waterfall，本地 `[memory_v2]` 优先。

### 步骤 11 — 会话事件流与外部会话

**`events.jsonl`（`xai-grok-session-events`）**：crate doc：「每会话事件日志（`events.jsonl`）。每条是一个类型化 `Event`。共享的 `EventWriter` 把条目以 JSON lines 追加。每会话的 `EventTracker` 为正在跑的 turn 保持状态，并从中派生事件。」

- `EventWriter`（`log.rs · EventWriter`）——追加写入器。
- `EventTracker`（`tracker.rs · EventTracker`）——turn 级状态机。
- `Const：EVENT_SCHEMA_VERSION = "1.0"`（`types.rs`）。
- `enum Event`（`types.rs · Enum：Event`）是主枚举，配套类型：`ToolCompletedSource`、`InterjectionSource`、`RedirectKind`、`McpErrorCategory`、`McpConfigServer`、`GoalClassifierVerdictTelemetry`、`GoalPauseReasonTelemetry`、`ToolOutcome`、`Phase`、`SessionRelationship`、`TurnOutcomeLabel`、`PermissionDecision`、`CancellationCategory`。

- 常量：`MAX_SESSIONS_PER_TOOL = 50`、`MAX_SESSION_AGE = 30 天`、`MAX_TITLE_CHARS = 200`、`MAX_FUTURE_SKEW = 5 分钟`（容忍时钟偏移）。

## 第四层 · 补全所有逻辑与技术要点

### 4.1 三层持久化职责划分（不要混淆）

同一份「会话」在磁盘上其实有三套并行记录，各有明确职责：

| 文件 | 生产者 | 消费者 | 关键特性 |
|------|--------|--------|---------|
| `chat_history.jsonl` | `ChatPersistence::persist_message` → `PersistenceMsg::Chat` | 模型上下文重建（resume） | `ConversationItem`，`CHAT_FORMAT_VERSION = 1`，可被压缩/rewind 整体替换 |
| `updates.jsonl` | `StorageAdapter::append_update*` | 前端重放、子代理重放、fork 复制 | `SessionUpdateEnvelope{timestamp, method, params}`，流式迭代，rewind 可过滤 |
| `events.jsonl` | `EventWriter` | 诊断/分析、**中断轮次识别** | 类型化 `Event`，`EVENT_SCHEMA_VERSION = "1.0"` |

为什么不全塞一个文件？因为它们的**读放大特征完全不同**：resume 要的是「模型上下文」这种小而定型的序列；重放要的是「逐条 UI 通知」且必须能流式、能 rewind 过滤、能按 offset 做增量；诊断要的是「结构化事实」且要求 schema 稳定。混在一起会让每一方都为另一方的需求付代价（这正是 `PersistedDataLight` 不带 `updates` 的原因）。

### 4.2 「丢失契约」是怎么被工程化的

`session/persistence.rs` 那段丢失契约（步骤 2）不是文档口号，而是三层机制合起来的结果：

```
第 1 层：写入调度
  PersistenceMsg 单一 FIFO → 同一会话不会有两个写者并发
  调用方 await 的写（FlushAndAck / AppendUpdateDurablyAndAck / AppendCwdSwitchAndAck）
  在 ack 时已在稳定介质上
第 2 层：文件级
  fs2 建议锁（lock_append）+ append 模式 + torn-line 自愈（补 \n）
  错误分级：NotCommitted（write_all 前）/ Committed（write_all 后）
  Buffered vs Durable 由 AppendDurability 决定是否 fsync file + parent
第 3 层：目录级
  原子 rename 写先 fsync 临时文件再 rename
  首次创建额外 sync 父目录；会话目录创建 sync 每一级新目录
  → 首次创建的 summary.json 在写返回时即持久
```

**失败的缓冲写会 latch**：这是最容易忽略的一条。如果一次流式 update 追加失败，actor 不会「跳过它继续 sync 后面的」——它把这个错误闩住，直到下一个屏障，届时屏障**返回这个错误**而不是 ack 一个陈旧状态的 sync 成功。否则调用方会以为自己等到了一个包含最新数据的屏障。

**测试怎么验证**：`with_update_append_probe` / `with_file_sync_probe` / `with_parent_sync_probe` 三个探针让你能在「append 之后但 file sync 之前」「file sync 之后但 parent sync 之前」精确注入失败（对应测试文件 `jsonl/durable_tests.rs`、`jsonl/tests.rs`、`jsonl/copy_tests.rs`）。

### 4.3 恢复的三层如何互补

```
异常退出（SIGSEGV / SIGBUS / SIGABRT）
   │
   ├─▶ ① xai-crash-handler 的 sigaction 处理器
   │      写 {crash_dir}/last-crash.bin（leader 是 crash/leader/）
   │      （signal / si_code / si_addr / timestamp / app_version / 栈）
   │      ↓ 下次启动
   │      check_previous_crash → 符号化 → last-crash-report.txt
   │                            → 归档 history/crash-{ts}.txt（保留 5 份）
   │      ⇒ 回答"进程怎么死的"
   │
   └─▶ ② 没有走到 try_unregister
          active_sessions.json 里那条 ActiveSession 留下
          ⇒ 下次 **register** 时被 retain 剪掉（不再有启动扫描）
          ⇒ 回答"哪些 PID 已经不在"（注册表自洁，不是 UI 提示）

任何退出方式（含 kill -9 / OOM / 断电）只要上一轮 turn 没闭合
   │
   └─▶ ③ events.jsonl 里最后一条 turn 事件是 turn_started
          ↓ 下次 session/load
          MvpAgent::record_interrupted_turn
            → detect_interrupted_turn → InterruptedTurn
            → updates.jsonl 补 turn_completed（前端画出结束标记）
            → events.jsonl 补 TurnEnded{Interrupted}（下次加载不再重复识别）
          MvpAgent::finish_interrupted_turn
            → SessionCommand::NoteInterruptedTurn → 模型收到 system reminder
            → 补传 turn_result.json（completed:false, stop_reason:"interrupted"）
          ⇒ 回答"哪一轮被打断了，模型要不要知道"
```

三层为什么都要有：① 只在**信号**死亡时才产生；② 只在**进程没走到注销**时才产生，而且当前 HEAD 它已退化为「自洁」而非「提示」；③ 只要**turn 没闭合**就成立——包括 `kill -9`、OOM、断电这些不给信号处理器机会的场景，而且它是唯一会**主动告知模型**的一层。`kill -9` 会让 `try_unregister` 拿不到锁而返回 `Ok(false)`——源码注释直接接受这一点：「孤儿会在下次 `register` 被剪掉」。也就是说「不清理」是设计允许的失败模式，而不是 bug。

### 4.4 rewind 与 fork 的语义差别（容易混）

| | fork | rewind |
|---|------|--------|
| 产物 | **新会话**（新 id、新目录、新文件） | **同一个会话**，历史被截断 |
| 源会话 | 保持不变 | 被就地改写（`replace_history` / `filter_rewind_updates`） |
| 粒度 | 可到 `target_prompt_index` | 每个 prompt 一个检查点（`[0..N-1]`） |
| 文件快照 | 复制父的 `compaction/` 段与 checkpoint | `file_state.rs` 的 `rewind_files` 把工作区文件回滚 |
| 父关系 | `parent_session_id` + `session_kind`（`"fork"` / `"worktree"`） | 无新关系 |
| 何时用 | 「从这一步分叉去试另一个方案，别弄脏原会话」 | 「这一步走错了，退回去重来」 |

两者共享同一个基础能力：**prompt 索引是稳定的对齐点**。fork 的 `target_prompt_index` 与 rewind 的 `prompt_index` 都是「第几个用户 prompt」，因此都能用同一套 `rewind_points` / `RewindPointMeta` 数据来定位。

### 4.5 检索索引的三个工程点

1. **可重建**：`recovery` 把不可用库文件分类 → 隔离 → 重建空库；`db` 加打开重试。索引永远不是真相源，坏了就重建（真相在 `updates.jsonl` / `chat_history.jsonl`）。
2. **跨进程安全**：`bootstrap` 的 lease 在**索引自己的 `meta` 表**里（`META_KEY_BOOTSTRAP_CLAIM` / `META_KEY_LAST_BOOTSTRAP`，`fts.rs`），不引入额外的锁文件。lease 300s、refresh 30s、peer wait 60s、poll 1s，并且有两处编译期 assert 保证「refresh 在 lease 内多次触发」「waiter 在 peer wait 内至少轮询一次」。等待者不是空转，而是「采纳同伴已完成的 bootstrap marker」。
3. **写压力控制**：`manager` 对同一会话的多次 upsert **去抖**（`flush_ready` 批量落盘）；`BootstrapProgress` 用单个 `AtomicU64` 同时装标志与 generation，使「清标志」这个操作在有更新的 set 介入时自动失败——避免把新一轮 bootstrap 的标志误清。

另外还有两层「跳过」优化：`SearchIndexStatus` 里的 `skipped`（因大小上限或超时跳过）与 `unchanged`（内容 hash 未变而跳过，`upsert_unless_unchanged`）。`should_skip_session` / `build_session_doc` / `UpsertOutcome` 都在 `doc.rs`。

### 4.6 记忆系统为什么必须「两条流水线」

`crates/codegen/xai-grok-memory/src/lib.rs` 的 crate doc 第一句就是「两条隔离的流水线。它们不共享文件、搜索、flush 或 Dream」——这是一个**刻意的迁移策略**，不是没整理干净：

- legacy 用 markdown 树 + `MEMORY.md` 精选，人类可读、可直接编辑、diff 友好；
- v2 用 topics + 不可变 observation inbox + Dream/consolidation，可做「先记录后整理」、可做 shadow 评估、可做保留策略与 GC；
- 两者**永不互读**，所以 v2 可以在 `MemoryV2Rollout::Shadow` 下「只评估计划、不提交 topic 变更」，用真实数据验证后再切 `Active`；
- 唯一的桥是**单向搬运**：`carry_over_legacy_memory`（`v2_carryover.rs`）+ `default_legacy_memory_root` / `legacy_memory_file`，把 legacy 的 markdown 段落导入成 v2 topic（报告 `topics_created` / `topics_appended` / `sections_skipped`）。

`MemoryV2Rollout` 的四态是这个策略的开关粒度：`Off`（禁用 v2 的一切读/捕获/Dream/写）→ `RecordOnly`（持久化抽取出的 observation，但不暴露给 manifest 与 Dream）→ `Shadow`（评估捕获与 Dream 计划，但不提交 curated topic 变更）→ `Active`（完整流水线）。`restrict()` 让多处 rollout 配置合并时取最保守值——这样远端配置不可能把本地更严的设置放宽。

v2 还有一条硬约束：**拒绝网络文件系统**（`UnsupportedNetworkFilesystem`）。理由与 `xai-sqlite-journal` 同源——v2 依赖本地共享内存协调（SQLite 状态库 + 词法索引），NFS 上不成立。

### 4.7 设计不变量小结（本章范围内）

1. **单一写者**：同一会话的所有文件写经 `PersistenceMsg` 一条 FIFO；文件级再叠一层 `fs2` 建议锁，双保险。
2. **丢失边界明确**：fire-and-forget 写可丢到「当前 turn 尾部」；await 的写在 ack 时已持久；失败的缓冲写**latch 到下一个屏障并让屏障报错**。
3. **追加自愈**：`append_jsonl_line_sync_with` 检测 torn trailing line 并补 `\n`，崩溃残行不会污染下一条记录。
4. **格式可演进**：`Summary` 的新字段全部可选，旧会话文件不会因新增字段加载失败（`persistence_head_fields_tests.rs` 钉住）；标题边界有显式的 `validate_rename_title` 拒绝路径与 `sanitize_and_cap_title` 截断路径，二者分工固定。
5. **fork 不变源**：fork 只创建新文件、不动源会话；`new_session_id` 恒为 36 字符 UUIDv7；backend 同步在后台 spawn，不在关键路径。
6. **rewind 有稳定对齐点**：prompt 索引既是 fork 的截断点，也是 rewind 的检查点；文件快照元数据与内容分离、惰性加载，且元数据/内容读取都收在 `FileStateTracker` 的方法上。
7. **恢复三层互补**：进程级 crash blob（`xai-crash-handler`，报告 0600、归档保留 5 份、leader 用独立目录）+ 活跃会话注册表（`xai-grok-active-sessions`，标准库 `try_lock` + 2s 有界获取 + 原子 rename + PID 存活判定，`EPERM` 视为存活，死 PID 由下次 `register` 剪掉）+ **未闭合 turn 识别**（`interrupted_turn`，同时补 `updates.jsonl` / `events.jsonl` / 模型提醒 / trace 结果）。
8. **检索可重建、跨进程安全、写压力受控**：FTS5 缓存坏了就隔离重建；全量重建带 meta 表 lease；upsert 去抖 + 内容 hash 跳过。
9. **SQLite 模式随文件系统走**：网络挂载用 TRUNCATE + per-host 文件名，避免 WAL 的 mmap `-shm` 在 NFS 上触发 SIGBUS；`GROK_SQLITE_JOURNAL_MODE` 是现场 kill-switch。
10. **记忆双流水线互不干扰**：legacy（markdown 树）与 v2（topics + observation + Dream）不共享任何文件；v2 用 rollout 四态灰度，单向 `carry_over_legacy_memory` 搬运，且拒绝网络文件系统。
