# 13 · 持久化、记忆与会话恢复

> **场景**：grok 关掉后，四样东西要能跨进程/跨会话存活——(1) **会话**：一次对话的完整状态（摘要 + 对话历史 + 事件流 + 各类状态文件），能被「恢复」「fork」「rewind」；(2) **崩溃恢复**：异常退出后，下次启动能找出孤儿会话，也能找回上一轮的进程级崩溃报告；(3) **检索**：在本机几百个会话里做全文搜索；(4) **记忆**：跨会话沉淀的知识（如「这个项目的构建命令是 X」）。
>
> **阅读说明**：源码基准 = 当前 HEAD（`6c01b90c`，2026-09-20）。**工具版本**：Rust `1.94.0`（`rust-toolchain.toml:11`）；`ratatui 0.29 / tokio full / agent-client-protocol 0.10.4`。
>
> 涉及 crate：`xai-chat-state`（会话状态的 actor + 持久化 trait）、`xai-grok-shell/src/session`（JSONL 存储实现 + 会话持久化 actor + fork/rewind）、`xai-grok-memory`（跨会话记忆，**legacy 与 v2 两条互不相通的流水线**）、`xai-grok-session-events`（`events.jsonl`）、`xai-sqlite-journal`（SQLite journal 模式选择）、`xai-grok-session-search`（SQLite FTS5 全文索引）、`xai-grok-foreign-sessions`（Claude/Codex/Cursor 会话只读扫描）、`xai-grok-active-sessions`（TUI 会话崩溃恢复）。
>
> 本文全部索引用「**文件路径 + 函数/类型名 + 函数内相对偏移（+0 = 函数定义行）**」。绝对行号随版本漂移，请以当前源码为准。

## 第二层 · 一个完整例子（全路径走读）

以「用户上次会话崩了，今天重新打开 grok，想找回那个会话并让模型记得项目约定」为例：

```
① 进程启动（xai-grok-pager-bin/src/main.rs）
   xai_crash_handler::check_previous_crash(grok_home()/crash)   lib.rs:104
     → 有 last-crash.bin 则符号化 + 写 last-crash-report.txt + 归档 history/
   随后（另一条线）：
   xai_grok_active_sessions::collect_crashed()   active-sessions/lib.rs:42
     → collect_crashed_in(grok_home)              :68
       读 active_sessions.json（持 flock），按 is_pid_alive(pid) 分区
       存活的留下、PID 已死的挑出来返回，并原子回写文件
     → 非空则记日志 "Found crashed sessions from a previous run"
        │
② 用户从列表点开那个会话 → 从磁盘加载：
   JsonlStorageAdapter::load_session(..)（实现 StorageAdapter，jsonl/mod.rs:1184）
     读 summary.json（标题/模型/head_commit/head_branch/…）
     读 chat_history.jsonl（CHAT_FORMAT_VERSION = 1，persistence.rs:50）
     读 updates.jsonl（SessionUpdateEnvelope 逐行，含 timestamp）
     读 plan.json / plan_mode_state.json / signals.json / goal_mode_state.json
     rewind_points.jsonl 走惰性加载（FileStateTracker），不在 resume 热路径上
        │
③ 会话恢复后，模型要回答「这个项目怎么构建」：
   记忆系统先召回跨会话知识：
   MemoryMode::Legacy → 读 {workspace_hash}/MEMORY.md（项目级）
                        + ~/.grok/memory/MEMORY.md（全局级）
   MemoryMode::V2     → 读 {scope}/topics/*.md + 生成的 MEMORY.md 清单
        │
④ 若记忆里没有，模型这轮产出的「构建约定」会被写回记忆：
   legacy: embed_missing_chunks(index, provider)  memory/lib.rs:89
           （分批 32 条补向量嵌入，支撑语义检索）
   v2:     capture → observation inbox → Dream/consolidation → topics
           （见 v2_capture.rs / v2_consolidation.rs / dream.rs）
        │
⑤ 用户想翻「上周那次讨论 OAuth 的会话」：
   session_search::execute_search(manager, root, &req)  manager.rs:233
     → 等首次 bootstrap 最多 BOOTSTRAP_WAIT_TIMEOUT
     → SQLite FTS5 BM25 查询 sessions/session_search.sqlite
     命中后按 cwd 解析出真实会话目录再打开
        │
⑥ 会话跑到一半崩溃（SIGSEGV）：
   xai-crash-handler 的 sigaction 处理器写 last-crash.bin（含 signal/si_code/栈）
   active_sessions.json 里的条目因为没走到 try_unregister 而留下
   → 下次启动就是 ① 的流程
```

链路说明：**会话是「单次、可恢复、可 fork/rewind、可搜索」；崩溃恢复分两层（进程级 crash blob + 会话级孤儿条目）；记忆是「长期、跨会话、按工作区」**。三者都落在 `~/.grok/` 下不同子目录，互不干扰。

## 第三层 · 详细逐步说明（主链路拆解）

### 步骤 1 — 会话状态 actor 与持久化 trait（`xai-chat-state`）

`xai-chat-state/src/lib.rs` 的 crate doc（偏移：+0 ~ +24）给出架构图：`SessionActor` 用 Command 与 `ChatStateActor` 通信，后者跑在专用 tokio 任务里，内部 `State` **无需锁**（`conversation: Vec<ConversationItem>`、`sampling_config`、`prompt_index`、`total_tokens`），事件经 `event_tx` 回推 `Session`。crate doc 还点名它「从 `xai-grok-shell` 的 `acp_session.rs` 抽出来，沿用与 `xai-hunk-tracker` 相同的 actor 模式」。

`trait ChatPersistence: Send + 'static`（`persistence.rs` 偏移：+16 ~ +39）是持久化的**唯一入口**，五个方法：

| 方法 | 语义 | 是否有 ack |
|------|------|-----------|
| `persist_message(&mut self, item: &ConversationItem)` | 追加单条到 `chat_history.jsonl` | 无（fire-and-forget） |
| `persist_working_directory_switch_and_ack(&mut self, item)` | 持久化一次 cwd 切换「代（generation）」 | 有（`oneshot<Result<StrictAppendAck, StrictAppendError>>`） |
| `replace_history(&mut self, items: &[ConversationItem])` | 整体替换历史（压缩 / rewind） | 无 |
| `replace_history_for_strip_and_ack(&mut self, items)` | **破坏性**的图片剥离重写：先备份磁盘历史再替换 | 有（`oneshot<io::Result<()>>`） |
| `flush(&mut self)` | 冲刷待写 | 无 |

注释把设计约束写死（偏移：+2 ~ +6）：「actor **独占** `Box<dyn ChatPersistence>`，所以 trait 方法取 `&mut self` —— 无锁、无原子、无共享状态。真实实现包着一个 actor 独占的 sender。」`replace_history_for_strip_and_ack` 的注释补了一条安全约束：**备份失败会 gate 掉重写**，这样「可恢复性」不会悄悄蒸发。

`enum StripOutcome`（偏移：+44 ~ +57）把剥离结果分成四态，注释点出动机：「类型化，这样一个死掉的 actor 绝不可能伪装成『什么都没剥离』」：

- `Applied { stripped: usize }` —— 已剥离且持久化（同一 URL 存两次算两次）；
- `NoMatch` —— 没有存量图片匹配请求的 URL；
- `WriteFailed { stripped: usize }` —— 内存已剥离但备份或落盘失败，**按未持久化处理**（下次加载会被重新污染）；
- `ActorUnavailable` —— chat-state actor 已死，剥离可能根本没发生。

同文件还有两个测试替身：`MockChatPersistence`（偏移：+80，用 `mpsc::UnboundedSender<PersistenceRecord>` 把每次调用报告给测试；`new_failing_strip_writes` 偏移：+119 专门钉「诚实失败」那一半契约；`new_with_manual_persistence_ack` 偏移：+126 让 ack 由测试掌控）与 `NullChatPersistence`（偏移：+248，全丢，给 benchmark / noop 场景）。`enum PersistenceRecord`（偏移：+64）是记录类型：`Message` / `AcknowledgedMessage` / `ReplaceHistory` / `ReplaceHistoryForStrip` / `Flush`。

### 步骤 2 — 生产实现：通道适配 + 单一写入 actor

`xai-grok-shell/src/session/chat_persistence.rs` 的 `ChannelChatPersistence`（偏移：+9）是 `ChatPersistence` 的生产实现——**它只做一件事：把调用翻译成 `PersistenceMsg` 发到 session 持久化 actor 的 channel**：

```
ChatPersistence::persist_message            → PersistenceMsg::Chat(item)
ChatPersistence::persist_working_directory_switch_and_ack
                                            → PersistenceMsg::AppendCwdSwitchAndAck{item, respond_to}
ChatPersistence::replace_history            → PersistenceMsg::ReplaceChatHistory(items)
ChatPersistence::replace_history_for_strip_and_ack
                                            → PersistenceMsg::ReplaceChatHistoryForStripAndAck{messages, respond_to}
ChatPersistence::flush                      → PersistenceMsg::Flush
```

两个 ack 路径都有一个「channel 已关」的兜底分支（偏移：+36 ~ +44 与 +59 ~ +73）：**发不出去也必须 ack 一个错误**，而不是挂住或假成功——`channel_persistence_acks_strip_error_when_actor_gone` 单测专门钉这条（偏移：+143）。

`xai-grok-shell/src/session/persistence.rs` 的模块 doc（偏移：+0 ~ +14）给出了这个 actor 的**硬掉电丢失契约**，这是本章最值得记住的一段：

- 即发即忘的写（流式 chunk、turn 中段的工具记录、feedback / btw_history 追加）是**缓冲**的：自上一个屏障以来的任何内容都可能丢，但丢失范围被限制在「正在跑的这轮 turn 的尾部」。
- 任何调用方 **await** 的写（`FlushAndAck`、`AppendUpdateDurablyAndAck`、`AppendCwdSwitchAndAck`）在 ack 触发时**已在稳定介质上**。屏障只 sync 自上一个屏障以来变脏的文件。一个失败的缓冲写（chat 追加、流式 update…）会**latch（闩住）**到下一个屏障，届时屏障返回该错误，而不是去 sync 陈旧或缺失的字节然后 ack 成功。
- 原子 rename 写会在 rename 前 fsync 临时文件，所以替换文件得到的是旧内容或新内容，**绝不会是垃圾**。若是「创建」，还会额外 sync 所在目录；会话目录创建会 sync 新建链条经过的每一级目录。所以首次创建（一个会话的第一个 `summary.json` 及其所在会话目录）在写返回时就是持久的。Windows 没有目录 fsync，那里 NTFS 元数据日志可能把一次极新的创建回滚成「不存在」，但**不会回滚成垃圾**。

`PersistenceMsg` 是一个大枚举（`persistence.rs`），实测变体覆盖：`Update` / `AppendUpdateDurablyAndAck` / `Chat` / `AppendCwdSwitchAndAck` / `ReplaceChatHistory` / `ReplaceChatHistoryForStripAndAck` / `Flush` / `FlushAndAck` / `ProbeWritable` / `UpgradeToWriteback{auth_manager}` / `StampSessionIdentity` / `SetRemoteAgentId` / `CurrentModel` / `PlanState` / `PlanModeState` / `GoalModeState` / `DeleteGoalModeState` / `WorkflowRunState` / `WorkflowRunStateAndAck` / `DeleteWorkflowRunState` / `ContentChunk` / `GeneratedTitle` / `RegenerateTitle` / `LastRecap` / `ManualTitleRenamed` / `ResetTitleToAuto` / `LastTurnSummary` / `RewindPoint` / `TruncateRewindPoints{from_index}` / `MergeRewindPointsFrom{target_index}` / `CollectionId` / `NextTraceTurn` / `WakeStart` / `WakeAbort{prior, respond_to}` / `HoldForTest` / `Signals` / `UsageTurn{turn_number, live}`。**所有会话文件写都走这一条 FIFO**——这是「同一会话不会有两个写者互相打架」的机制保障。

三个冲刷层级：`flush_pending`（写缓冲区 → 文件）、`flush_and_sync`（再 fsync 变脏文件）、`flush_and_sync_all`（全部）。

### 步骤 3 — JSONL 落盘层（`StorageAdapter` + `JsonlStorageAdapter`）

`xai-grok-shell/src/session/storage/mod.rs` 的文件常量（`pub(crate) const`）：`SUMMARY_FILE = "summary.json"`、`PLAN_FILE = "plan.json"`、`CHAT_HISTORY_FILE = "chat_history.jsonl"`、`UPDATES_FILE = "updates.jsonl"`。

`trait StorageAdapter: Send + Sync`（偏移：+1166 起，即 1167 行起）是存储后端的抽象（注释：「Abstracts over different storage backends (JSONL, SQLite, etc.)」）。除 `init_session` 外，方法可粗分为四组：

- **标题/元数据**：`update_session_title`（+2，手动 `/rename`，last-write-wins）、`set_generated_title_if_absent`（+11，自动生成标题**绝不覆盖**手动改名）、`regenerate_generated_title`（+20，早期会话在第 3、6 轮刷新自动标题，但**永不覆盖**手动 pin——注释强调「手动检查与写在 summary 锁下原子，因此并发手动改名总是赢」）、`reset_title_to_auto`（+40，`/rename --auto`）、`set_last_recap`（+42）、`set_last_turn_summary`（+46）。
- **身份/种类**：`stamp_session_identity`（+26，在 summary 锁下原子写「获胜的 root identity」）、`set_session_kind_if_absent`（+33，只在该会话还没有 kind 时才写——磁盘上已有的 kind（崩溃恢复目录、并发写者）会被保留）。
- **追加**：`append_update`（+54）、`append_update_commit_aware`（+57，报告「重放记录是否在错误前已提交」）、`append_update_durable_commit_aware`（+67，默认实现返回 `Unsupported`，由 JSONL 实现覆盖）、`append_chat_message`（+79）、`append_chat_message_commit_aware`（+84，注释说明记账（summary 计数器）可能在 append 已进 page cache 之后失败）、`append_cwd_switch_commit_aware`（+95）。
- **读取/复制**：`load_session` / `copy_session_data` / `copy_session_data_sync`（fork 用）等。

**「commit-aware」这一族方法的语义**值得单独说：它们区分「JSONL 记录已提交」与「记账失败」，因为这两件事的恢复策略完全不同——记录没提交可以安全重放，记账失败则不能重复追加。

`struct SessionFileSet { updates, chat, summary, plan, rewind_points }`（偏移：+1142）与 `SessionFileSet::ALL`（偏移：+1151）是「一次屏障要 sync 哪些文件」的集合。

**数据结构**：

- `enum SessionUpdate`（偏移：+677）——一个类型同时装两种通知：`Acp(Box<acp::SessionNotification>)`（method = `"session/update"`）与 `Xai(Box<SessionNotification>)`（method = `"_x.ai/session/update"`）。它的 `Serialize`（偏移：+685 ~ +705）**只写 `method` + `params`，不写 timestamp**，注释说明这是给 GCS 上传等消费者用的。
- `struct SessionUpdateEnvelope { timestamp, method, params }`（偏移：+720，`pub(crate)`）——这才是**真正写到 `updates.jsonl`** 的磁盘形态；注释解释为什么要分两个类型：「这样其它消费者（例如网络监听器）不会看到 timestamp 元数据」。`Xai` 分支序列化时会先 `without_live_agent_address()` 剥掉活体 agent 地址。

```rust
fn append_jsonl_line_sync_with(
    path: &Path,
    mut line: Vec<u8>,
    durability: AppendDurability,
    mut sync_file: impl FnMut(&std::fs::File) -> io::Result<()>,
    mut sync_parent: impl FnMut() -> io::Result<()>,
) -> Result<(), AppendLineError> {
    debug_assert!(line.ends_with(b"\n"), "JSONL record must end with \\n");
    let lock = Self::lock_append(path).map_err(AppendLineError::NotCommitted)?;
    let result = (|| {
        let mut file = OpenOptions::new().read(true).create(true).append(true)
            .open(path).map_err(AppendLineError::NotCommitted)?;
        let len = file.metadata().map_err(AppendLineError::NotCommitted)?.len();
        if len > 0 {
            file.seek(io::SeekFrom::Start(len - 1)).map_err(AppendLineError::NotCommitted)?;
            let mut last = [0u8; 1];
            file.read_exact(&mut last).map_err(AppendLineError::NotCommitted)?;
            if last[0] != b'\n' {
                tracing::warn!(path = %path.display(),
                    "jsonl file has a torn trailing line (previous append crashed mid-write?); \
                     terminating it before appending");
                line.insert(0, b'\n');
            }
        }
        file.write_all(&line).map_err(AppendLineError::NotCommitted)?;
        file.flush().map_err(AppendLineError::Committed)?;
        if matches!(durability, AppendDurability::Durable) {
            sync_file(&file).map_err(AppendLineError::Committed)?;
            drop(file);
            sync_parent().map_err(AppendLineError::Committed)?;
        } else { drop(file); }
        Ok(())
    })();
    let _ = lock.unlock();
    result
}
```

四个要点：(1) 全程持 `fs2` 建议性文件锁（`lock_append` 偏移：+593），**同会话并发写被串行化**；(2) **torn-line 自愈**——如果上一次追加在写一半时崩溃，文件最后一个字节不是 `\n`，这里会在新记录前补一个 `\n`，把残行终止掉，于是后续解析不会把两条记录粘成一条；(3) 错误分两级：`AppendLineError::NotCommitted`（write_all 之前失败）与 `Committed`（write_all 之后失败，此时记录至少进了 page cache）；(4) `AppendDurability::{Buffered, Durable}`（偏移：+21）控制是否做 `sync_file` + `sync_parent`。

围绕它的周边：`append_jsonl`（偏移：+371）默认 `Buffered`，`append_jsonl_with_durability`（偏移：+375）可指定，`append_jsonl_line_blocking`（偏移：+386）、`sync_file_path_durable`（偏移：+395）、`append_jsonl_line_sync`（偏移：+406）、`sync_file_durable`（偏移：+603）、`sync_parent_directory`（偏移：+606）、`lock_append`（偏移：+593）、`sync_parent_if_first_create_summary`（偏移：+735，**只在首次创建 `summary.json` 时 sync 父目录**）、`write_summary_sync`（偏移：+763）、`read_summary_sync`（偏移：+769）、`read_chat_history_sync`（偏移：+956）/`read_chat_history_sync_bounded`（偏移：+963）。

### 步骤 9 — SQLite journal 模式选择（`xai-sqlite-journal`）

这个 crate 存在的唯一理由是**网络文件系统上的 SIGBUS 隐患**。crate doc（`lib.rs` 偏移：+0 ~ +13）把因果链写全了：WAL 把 wal-index 放在 mmap 的 `-shm` 文件里，依赖一致共享内存 + 可靠的 POSIX 锁——这两样网络文件系统都不保证。当 `$HOME`（从而 `~/.grok`）是 NFS 挂载且被多台机器同时使用，同伴主机在 WAL 恢复或关闭期间截断/重建 `-shm`，会把我们映射的底层抽掉，下一次 wal-index 读就死于 SIGBUS。在这种挂载上改用 rollback journal（SQLite 官方文档就写了「WAL 不适用于网络文件系统」），并且**每台主机打开自己的 per-host DB 文件**（见 `effective_db_path`），这样任何同伴——包括那些会把它翻回 WAL 的修复前二进制——都不会共享该文件。

- `enum JournalMode { Wal, Truncate }`（偏移：+28），注释解释了为什么 Truncate 而不是 DELETE：「提交时截断（而非 unlink）——在网络文件系统上安全，且比 DELETE 模式便宜：没有每次提交的 create/unlink 命名空间往返，也没有 NFS 的 `.nfsXXXX` silly-rename 垃圾。」
- `JournalMode::for_db_path(db_path)`（偏移：+42 ~ +82）——`GROK_SQLITE_JOURNAL_MODE`（`wal`|`truncate`）可强制覆盖，作为现场 kill-switch；强制时 `tracing::info!` 记 `source = "env"`（注释：「让现场切换 kill-switch 在日志里可 grep」）；取值非法时 `tracing::warn!` 记非法值并回落到探测（「紧急 kill-switch 打错字必须响亮，不能静默忽略」）；否则按 `is_network_fs(parent_dir)` 选 Truncate 或 Wal，并记 `source = "statfs"` 的 debug 日志。注意它分类的是**父目录**（DB 文件本身可能还不存在），所以调用方必须先建目录。
- `JournalMode::effective_db_path(db_path)`（偏移：+86 ~ +112）——只有 Truncate 才改路径：插到最后一个扩展名前（`worktrees.db` → `worktrees.h-<host>.db`），无扩展名就追加；对已带 `-h-` 标签的路径幂等；拿不到 hostname 就退回原路径（仍是 TRUNCATE）。
- `JournalMode::open(db_path)`（偏移：+115 ~ +120）——在 `effective_db_path` 上打开读写连接并 `apply_with_retry`。
- 超时常量：`BUSY_TIMEOUT = 5000ms`（偏移：+20，注释：「等同伴的锁，而不是立刻失败；与所有消费方历史上的设置一致」）、`BUSY_RETRY_BUDGET = 10s`（偏移：+24，注释：「一个预算用于熬过 `SQLITE_BUSY`。内层重试共享调用方的 deadline，这样两个计时器不会叠加成两倍宣称等待」）。

`xai-grok-memory` 的 v2 流水线也直接用这个 crate（`v2.rs` 里 `use xai_sqlite_journal::JournalMode;`），并且对网络文件系统**直接拒绝**：`V2StorageError::UnsupportedNetworkFilesystem`（`v2.rs` 偏移：+60 ~ +63）的报文是「v2 memory scope … is on a network filesystem; memory-v2 requires local shared-memory coordination」。

## 第四层 · 补全所有逻辑与技术要点

### 4.1 三层持久化职责划分（不要混淆）

同一份「会话」在磁盘上其实有三套并行记录，各有明确职责：

| 文件 | 生产者 | 消费者 | 关键特性 |
|------|--------|--------|---------|
| `chat_history.jsonl` | `ChatPersistence::persist_message` → `PersistenceMsg::Chat` | 模型上下文重建（resume） | `ConversationItem`，`CHAT_FORMAT_VERSION = 1`，可被压缩/rewind 整体替换 |
| `updates.jsonl` | `StorageAdapter::append_update*` | 前端重放、子代理重放、fork 复制 | `SessionUpdateEnvelope{timestamp, method, params}`，流式迭代，rewind 可过滤 |
| `events.jsonl` | `EventWriter` | 诊断/分析 | 类型化 `Event`，`EVENT_SCHEMA_VERSION = "1.0"` |

为什么不全塞一个文件？因为它们的**读放大特征完全不同**：resume 要的是「模型上下文」这种小而定型的序列；重放要的是「逐条 UI 通知」且必须能流式、能 rewind 过滤、能按 offset 做增量；诊断要的是「结构化事实」且要求 schema 稳定。混在一起会让每一方都为另一方的需求付代价（这正是 `PersistedDataLight` 不带 `updates` 的原因）。

### 4.2 「丢失契约」是怎么被工程化的

`session/persistence.rs` 那段丢失契约（步骤 2）不是文档口号，而是三层机制合起来的结果：

```
第 1 层：写入调度
  PersistenceMsg 单一 FIFO → 同一会话不会有两个写者并发
  调用方 await 的写（FlushAndAck / AppendUpdateDurablyAndAck / AppendCwdSwitchAndAck）
  在 ack 时已在稳定介质上
第 2 层：文件级
  fs2 建议锁（lock_append）+ append 模式 + torn-line 自愈（补 \n）
  错误分级：NotCommitted（write_all 前）/ Committed（write_all 后）
  Buffered vs Durable 由 AppendDurability 决定是否 fsync file + parent
第 3 层：目录级
  原子 rename 写先 fsync 临时文件再 rename
  首次创建额外 sync 父目录；会话目录创建 sync 每一级新目录
  → 首次创建的 summary.json 在写返回时即持久
```

**失败的缓冲写会 latch**：这是最容易忽略的一条。如果一次流式 update 追加失败，actor 不会「跳过它继续 sync 后面的」——它把这个错误闩住，直到下一个屏障，届时屏障**返回这个错误**而不是 ack 一个陈旧状态的 sync 成功。否则调用方会以为自己等到了一个包含最新数据的屏障。

**测试怎么验证**：`with_update_append_probe` / `with_file_sync_probe` / `with_parent_sync_probe` 三个探针让你能在「append 之后但 file sync 之前」「file sync 之后但 parent sync 之前」精确注入失败（对应测试文件 `jsonl/durable_tests.rs`、`jsonl/tests.rs`、`jsonl/copy_tests.rs`）。

### 4.3 崩溃恢复的两层如何互补

```
信号（SIGSEGV/SIGBUS/SIGABRT）
   │
   ├─▶ xai-crash-handler 的 sigaction 处理器
   │      写 grok_home()/crash/last-crash.bin
   │      （signal / si_code / si_addr / timestamp / app_version / 栈）
   │      ↓ 下次启动
   │      check_previous_crash → 符号化 → last-crash-report.txt
   │                             → 归档 history/crash-{ts}.txt（保留 5 份）
   │      ⇒ 回答"进程怎么死的"
   │
   └─▶ 没有走到 try_unregister
          active_sessions.json 里那条 ActiveSession 留下
          ↓ 下次启动
          collect_crashed → 按 is_pid_alive 分区 → 返回死 PID 的条目
          ⇒ 回答"哪些会话需要恢复"

非信号类异常退出（kill -9、OOM、断电）
   ⇒ 只有第二层有效（没有信号处理器介入的机会）
   ⇒ 这也解释了为什么第二层必须存在，不能只靠 crash handler
```

反过来，`kill -9` 会让 `try_unregister` 的**非阻塞**版本（`try_unregister`）可能拿不到锁而返回 `Ok(false)`——源码注释直接接受这一点：「孤儿会在下次启动被 `collect_crashed` 清理」。也就是说「不清理」是设计允许的失败模式，而不是 bug。

### 4.4 rewind 与 fork 的语义差别（容易混）

| | fork | rewind |
|---|------|--------|
| 产物 | **新会话**（新 id、新目录、新文件） | **同一个会话**，历史被截断 |
| 源会话 | 保持不变 | 被就地改写（`replace_history` / `filter_rewind_updates`） |
| 粒度 | 可到 `target_prompt_index` | 每个 prompt 一个检查点（`[0..N-1]`） |
| 文件快照 | 复制父的 `compaction/` 段与 checkpoint | `file_state.rs` 的 `rewind_files` 把工作区文件回滚 |
| 父关系 | `parent_session_id` + `session_kind`（`"fork"` / `"worktree"`） | 无新关系 |
| 何时用 | 「从这一步分叉去试另一个方案，别弄脏原会话」 | 「这一步走错了，退回去重来」 |

两者共享同一个基础能力：**prompt 索引是稳定的对齐点**。fork 的 `target_prompt_index` 与 rewind 的 `prompt_index` 都是「第几个用户 prompt」，因此都能用同一套 `rewind_points` / `RewindPointMeta` 数据来定位。

### 4.5 检索索引的三个工程点

1. **可重建**：`recovery` 把不可用库文件分类 → 隔离 → 重建空库；`db` 加打开重试。索引永远不是真相源，坏了就重建（真相在 `updates.jsonl` / `chat_history.jsonl`）。
2. **跨进程安全**：`bootstrap` 的 lease 在**索引自己的 `meta` 表**里（`META_KEY_BOOTSTRAP_CLAIM` / `META_KEY_LAST_BOOTSTRAP`，`fts.rs`），不引入额外的锁文件。lease 300s、refresh 30s、peer wait 60s、poll 1s，并且有两处编译期 assert 保证「refresh 在 lease 内多次触发」「waiter 在 peer wait 内至少轮询一次」。等待者不是空转，而是「采纳同伴已完成的 bootstrap marker」。
3. **写压力控制**：`manager` 对同一会话的多次 upsert **去抖**（`flush_ready` 批量落盘）；`BootstrapProgress` 用单个 `AtomicU64` 同时装标志与 generation，使「清标志」这个操作在有更新的 set 介入时自动失败——避免把新一轮 bootstrap 的标志误清。

另外还有两层「跳过」优化：`SearchIndexStatus` 里的 `skipped`（因大小上限或超时跳过）与 `unchanged`（内容 hash 未变而跳过，`upsert_unless_unchanged`）。`should_skip_session` / `build_session_doc` / `UpsertOutcome` 都在 `doc.rs`。

### 4.6 记忆系统为什么必须「两条流水线」

`lib.rs` 的 crate doc 第一句就是「两条隔离的流水线。它们不共享文件、搜索、flush 或 Dream」——这是一个**刻意的迁移策略**，不是没整理干净：

- legacy 用 markdown 树 + `MEMORY.md` 精选，人类可读、可直接编辑、diff 友好；
- v2 用 topics + 不可变 observation inbox + Dream/consolidation，可做「先记录后整理」、可做 shadow 评估、可做保留策略与 GC；
- 两者**永不互读**，所以 v2 可以在 `MemoryV2Rollout::Shadow` 下「只评估计划、不提交 topic 变更」，用真实数据验证后再切 `Active`；
- 唯一的桥是**单向搬运**：`carry_over_legacy_memory`（`v2_carryover.rs`）+ `default_legacy_memory_root` / `legacy_memory_file`，把 legacy 的 markdown 段落导入成 v2 topic（报告 `topics_created` / `topics_appended` / `sections_skipped`）。

`MemoryV2Rollout` 的四态是这个策略的开关粒度：`Off`（禁用 v2 的一切读/捕获/Dream/写）→ `RecordOnly`（持久化抽取出的 observation，但不暴露给 manifest 与 Dream）→ `Shadow`（评估捕获与 Dream 计划，但不提交 curated topic 变更）→ `Active`（完整流水线）。`restrict()` 让多处 rollout 配置合并时取最保守值——这样远端配置不可能把本地更严的设置放宽。

v2 还有一条硬约束：**拒绝网络文件系统**（`UnsupportedNetworkFilesystem`）。理由与 `xai-sqlite-journal` 同源——v2 依赖本地共享内存协调（SQLite 状态库 + 词法索引），NFS 上不成立。

### 4.7 设计不变量小结（本章范围内）

1. **单一写者**：同一会话的所有文件写经 `PersistenceMsg` 一条 FIFO；文件级再叠一层 `fs2` 建议锁，双保险。
2. **丢失边界明确**：fire-and-forget 写可丢到「当前 turn 尾部」；await 的写在 ack 时已持久；失败的缓冲写**latch 到下一个屏障并让屏障报错**。
3. **追加自愈**：`append_jsonl_line_sync_with` 检测 torn trailing line 并补 `\n`，崩溃残行不会污染下一条记录。
4. **格式可演进**：`Summary` 的新字段全部可选，旧会话文件不会因新增字段加载失败（`persistence_head_fields_tests.rs` 钉住）。
5. **fork 不变源**：fork 只创建新文件、不动源会话；`new_session_id` 恒为 36 字符 UUIDv7；backend 同步在后台 spawn，不在关键路径。
6. **rewind 有稳定对齐点**：prompt 索引既是 fork 的截断点，也是 rewind 的检查点；文件快照元数据与内容分离、惰性加载。
7. **崩溃恢复双层**：信号级 crash blob（`xai-crash-handler`，报告 0600、归档保留 5 份）+ 会话级孤儿条目（`xai-grok-active-sessions`，flock + 原子 rename + PID 存活判定，`EPERM` 视为存活）。
8. **检索可重建、跨进程安全、写压力受控**：FTS5 缓存坏了就隔离重建；全量重建带 meta 表 lease；upsert 去抖 + 内容 hash 跳过。
9. **SQLite 模式随文件系统走**：网络挂载用 TRUNCATE + per-host 文件名，避免 WAL 的 mmap `-shm` 在 NFS 上触发 SIGBUS；`GROK_SQLITE_JOURNAL_MODE` 是现场 kill-switch。
10. **记忆双流水线互不干扰**：legacy（markdown 树）与 v2（topics + observation + Dream）不共享任何文件；v2 用 rollout 四态灰度，单向 `carry_over_legacy_memory` 搬运，且拒绝网络文件系统。
