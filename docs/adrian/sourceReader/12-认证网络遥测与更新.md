# 12 · 认证、网络、遥测与更新

> **场景**：grok 要连 LLM API，就得有 token；token 会过期，得刷新；每次请求要带 bearer 并在 401 时重试；整个过程要被遥测记录；崩溃要留得下报告；产品还要能在后台静默自更新。这五件事（认证 / 网络 / 遥测 / 崩溃上报 / 更新）是「能长期稳定跑起来的 Agent」的运维骨架。
>
> **阅读说明**：源码基准 = 当前 HEAD（`6c01b90c`，2026-09-20）。**工具版本**：Rust `1.94.0`（`rust-toolchain.toml:11`）；`ratatui 0.29 / tokio full / agent-client-protocol 0.10.4`。
>
> 五个子系统分别位于：`crates/codegen/xai-grok-auth`（认证 seam + 401 重试中间件）、`crates/codegen/xai-grok-login`（登录/刷新/存储，**已从 shell 抽出成独立 crate**）、`crates/codegen/xai-grok-http`（共享 reqwest 客户端与传输错误分类）、`crates/codegen/xai-grok-telemetry` + `crates/codegen/xai-grok-otel` + `crates/codegen/xai-mixpanel`（遥测栈）、`crates/codegen/xai-crash-handler`（崩溃处理，**注意不是 `xai-grok-crash-handler`**）、`crates/codegen/xai-grok-update`（自更新）。
>
> 本文全部索引用「**文件路径 + 函数/类型名 + 函数内相对偏移（+0 = 函数定义行）**」。绝对行号随版本漂移，请以当前源码为准。

## 第三层 · 详细逐步说明（主链路拆解）

### 步骤 1 — 认证依赖倒置 seam（`xai-grok-auth`，只有 5 个文件）

`xai-grok-auth/src/lib.rs` 的 crate doc（`偏移：+0 ~ +1`）明确写出 seam 的目的：介于 `xai-file-utils`（持有方）与 `xai-grok-shell`（实现方）之间，**让数据收集器的 import 图里不出现壳层类型**，同时仍能由「刷新感知的 token 解析」驱动 HTTP 请求。

模块面（`Module：xai-grok-auth` 偏移：`lib.rs` +6 ~ +10）：

- `visibility`（`visibility.rs`）—— 最基础的 `trait HttpAuth`（`偏移：+3`）：只有 `apply(&self, builder: RequestBuilder, base_url: &str) -> RequestBuilder` 一个方法（`偏移：+4`），注释点名实现方是 `xai-grok-shell::util::grok_auth_credentials::GrokAuthCredentials`。
- `auth_provider`（`auth_provider.rs`）—— `CredentialSnapshot`（`偏移：+11`）与 `trait AuthCredentialProvider: HttpAuth + Send + Sync + 'static`（`偏移：+32`）。
- `bearer_fragment`（`bearer_fragment.rs`）—— `BEARER_SUFFIX_LEN = 12`（`偏移：+5`）与 `fn bearer_suffix(s: &str) -> &str`（`偏移：+9`）。
- `retry_middleware`（`retry_middleware.rs`）—— **只有启用 `middleware` feature 才编译**（`lib.rs:8` 的 `#[cfg(feature = "middleware")]`）。

`CredentialSnapshot` 的六个字段（`auth_provider.rs` 偏移：+13 ~ +26）各自对应一处下游用途：

| 字段 | 语义 | 谁读 |
|------|------|------|
| `token` | wire bearer；CI / `--api-key` 无认证时为 `None` | 中间件、401 归因、OTel |
| `user_id` | bearer 属主 | OTel `user.id` resource attribute |
| `team_id` | OAuth 团队 id | 遥测 team 维度 |
| `deployment_id` | `uuidv5(NAMESPACE_OID, deployment_key)` | 企业部署归因 |
| `api_key_id` | `uuidv5(NAMESPACE_OID, api_key)` | `AuthMode::ApiKey` 归因 |
| `organization_id` | OIDC `organizationId` claim | 组织维度 |

`trait AuthCredentialProvider` 有四个成员（`auth_provider.rs` 偏移：+4 ~ +22）：

- `fn snapshot(&self) -> CredentialSnapshot` —— 契约写明：实现方应在快照前做一次**廉价的磁盘重读**，这样调用方能看见兄弟进程（`grok-desktop`、`grok login`）的更新；并且 `token` 字段**必须**与 `HttpAuth::apply` 实际发到线上的 bearer 一致，否则 401 归因前缀会对不上。
- `async fn refresh_after_unauthorized(&self) -> bool` —— 返回 `true` 表示拿到了不同的 token，调用方应重试一次；`false` 表示没配置 refresher 或刷新失败。
- `fn needs_token_auth_header(&self) -> bool`（默认 `true`）—— 是否发 `X-XAI-Token-Auth`；deployment key 走裸 Bearer 时为 `false`。
- `fn has_usable_credential(&self) -> bool`（默认 `true`）—— 是否值得真发一次出站请求。

`StaticAuthCredentialProvider`（`auth_provider.rs` 偏移：+60）是测试/简单场景用的静态实现：`new(inner: Box<dyn HttpAuth>, bearer: Option<String>)`（偏移：+8），`snapshot()` 只填 `token`（偏移：+29），`refresh_after_unauthorized()` 恒返回 `false`（偏移：+36）。它的 `Debug` 只打印 `has_bearer` 布尔（偏移：+13），刻意不落 token。

### 步骤 2 — 网络层：共享客户端 + bearer/401 中间件

`xai-grok-http` 是本次重构新抽出的一层（crate doc `偏移：+0 ~ +6` 说明动机：构造 `reqwest::Client` 很贵，约 95ms，因为要加载 OS TLS roots，所以共享客户端用 `OnceLock` 缓存；TLS 策略住在 `xai_grok_extra_ca`）。

**常量与它们的编译期断言**（`xai-grok-http/src/lib.rs` 偏移：+13 ~ +58）——这层把超时预算写成常量，并用 `const _: () = assert!(...)` 把「谁必须大于谁」编码进编译期：

| 常量 | 值 | 语义 |
|------|-----|------|
| `STARTUP_FETCH_TIMEOUT` | 5s | 单次启动 `/settings` 或 `/v1/models` 抓取的每次尝试上限 |
| `STARTUP_AUTH_TIMEOUT` | 60s | 非交互启动期认证（刷新或冷启动 mint）总预算 |
| `STARTUP_AUTH_REFRESH_TIMEOUT` | 5s | 单次启动 token 刷新往返 |
| `SETTINGS_REAPPLY_TIMEOUT` | 30s | 单个 settings-reapply 任务的外层上限 |
| `SETTINGS_FETCH_MAX_ATTEMPTS` | 3 | 后台 settings 抓取尝试次数 |
| `SETTINGS_RETRY_BACKOFF_STEP` | 500ms | 尝试之间的退避步长 |
| `STARTUP_SETTINGS_WAIT_DEADLINE` | 5.5s | 一次抓取超时 + 一次退避 |
| `MANAGED_STARTUP_SETTINGS_WAIT_DEADLINE` | 25s | managed 场景下最坏三次尝试阶梯 |
| `MIN_CLIENT_CONNECT_TIMEOUT` | 120s | 客户端连 leader 的下界（≥ 2× `STARTUP_AUTH_TIMEOUT`） |

**`shared_client()`**（`lib.rs` 偏移：+0 ~ +18，即 266~284）——`OnceLock<reqwest::Client>`，`get_or_init` 里先开一个 `startup_timer!("startup.http_client_build")` 埋点，然后经 `xai_grok_extra_ca::build_reqwest_client` 装配：`connect_timeout(30s)`、`user_agent(process_user_agent_string())`、`pool_idle_timeout(30s)`、HTTP/2 keep-alive 20s / timeout 10s / `while_idle(true)`、`tcp_keepalive(30s)`。失败直接 `expect("failed to build shared HTTP client")`。

**`with_auth_retry(client, credentials)`**（`lib.rs` 偏移：+0 ~ +7，即 286~293）——把任意 `reqwest::Client` 包成带认证重试的 `ClientWithMiddleware`：

```rust
pub fn with_auth_retry(
    client: reqwest::Client,
    credentials: std::sync::Arc<dyn xai_grok_auth::AuthCredentialProvider>,
) -> reqwest_middleware::ClientWithMiddleware {
    reqwest_middleware::ClientBuilder::new(client)
        .with(xai_grok_auth::AuthRetryMiddleware::new(credentials, 1))
        .build()
}
```

注意 `max_retries` 硬编码为 **1**：全应用统一「401 只刷新重发一次」。

**另外三个客户端**：`shared_upload_client()`（偏移：+29 ~ +43，`http1_only` + `pool_max_idle_per_host(2)` + 10s idle）、`fresh_http1_client()`（偏移：+45 ~ +52，`pool_max_idle_per_host(0)`，用于「逃出连接池」）、`shared_startup_blocking_client()`（偏移：+205 ~ +221，`reqwest::blocking`，`connect_timeout`/`timeout` 都取 `STARTUP_FETCH_TIMEOUT`）。

**传输错误分类**：`enum TransportFailureKind`（偏移：+87 ~ +94）有 `Unreachable` / `CertificateUntrusted` / `CertificateInvalid` / `Interrupted` / `Permanent` 五态；`TransportFailure::classify(&reqwest::Error)`（偏移：+103 ~ +114）先用 `certificate_error(e)` 沿 source 链找 `rustls::Error::InvalidCertificate`（`UnknownIssuer` → `UntrustedIssuer`，其余 → `Other`），再按 `is_connect()` / `is_timeout()||is_request()||is_body()` 分派（`transport_kind` 偏移：+116 ~ +128）。`find_os_error_code`（偏移：+65 ~ +77）沿 source 链下钻 `std::io::Error::raw_os_error`，找不到时退回解析 `"(os error N)"` 文本（`parse_os_error` 偏移：+79 ~ +85）——测试里用真实 connection reset 与真实 TLS 握手来钉这条分类。

**`send_with_retry_escaping_pool`**（偏移：+156 ~ +203）——泛型重试组合子：`max_attempts.max(1)`，前 `n-1` 次用 pooled client，**最后一次**换成 `fresh_http1_client()`（惰性构造并缓存），每次重试前 `await backoff(attempt)`；`is_retryable` 为假时立即返回错误，否则记 `last_err` 继续；循环结束返回最后一个错误。

### 步骤 3 — 401 重试中间件（真实函数体拆解）

`xai-grok-auth/src/retry_middleware.rs` 把「刷新感知的 HTTP 重试」做成 `reqwest_middleware::Middleware`，而不是让调用方写循环。四个关键符号：

**`StampedBearerSuffix(pub String)`**（偏移：+14）——只存 bearer 的**尾部**片段（`BEARER_SUFFIX_LEN = 12`）。crate 注释给了理由：JWT 头部是共享常量、xAI key 前缀也是共享的，只有尾部能区分；而且尾部可以安全落日志。

**`fn bearer_suffix(s: &str) -> &str`**（`bearer_fragment.rs` 偏移：+9 ~ +14）——用 `char_indices().rev().nth(N-1)` 取**字符**而非字节，注释点名原因：从 `auth.json` 或 auth-provider 命令来的 token 可能非 ASCII，按字节切会 panic。单测覆盖了 `"ééééééééééééé"` 与 emoji 用例。

**`async fn execute_with_stamp(client, req)`**（偏移：+19 ~ +26，即 20~27）——入口，把实际发出的 bearer 后缀带回来：

```rust
pub async fn execute_with_stamp(
    client: &reqwest_middleware::ClientWithMiddleware,
    req: Request,
) -> reqwest_middleware::Result<(Response, Option<StampedBearerSuffix>)> {
    let mut ext = http::Extensions::new();
    let resp = client.execute_with_extensions(req, &mut ext).await?;
    Ok((resp, ext.get::<StampedBearerSuffix>().cloned()))
}
```

**`fn apply_auth_header(req, token, extensions)`**（偏移：+42 ~ +53，私有）——`HeaderValue::from_str(&format!("Bearer {token}"))` 成功则写 `AUTHORIZATION` 头并把 `StampedBearerSuffix(bearer_suffix(token))` 插进 extensions；失败只 `tracing::warn!`（不 panic）。

**`impl Middleware for AuthRetryMiddleware::handle`**（偏移：+57 ~ +98，即 58~99）——真正的 401 循环：

```rust
async fn handle(&self, mut req, extensions, next) -> Result<Response, Error> {
    if let Some(ref token) = self.credentials.snapshot().token {
        apply_auth_header(&mut req, token, extensions);
    }
    let backup = req.try_clone();
    let resp = next.clone().run(req, extensions).await?;
    if resp.status() != StatusCode::UNAUTHORIZED || self.max_retries == 0 {
        return Ok(resp);
    }
    let Some(backup) = backup else { return Ok(resp) };
    let _retry_span = tracing::info_span!("auth.retry_401");
    let mut last_resp = resp;
    for _ in 0..self.max_retries {
        if !self.credentials.refresh_after_unauthorized().await { break; }
        let Some(ref token) = self.credentials.snapshot().token else { break; };
        let Some(mut retry) = backup.try_clone() else { break; };
        apply_auth_header(&mut retry, token, extensions);
        last_resp = next.clone().run(retry, extensions).await?;
        if last_resp.status() != StatusCode::UNAUTHORIZED { return Ok(last_resp); }
    }
    Ok(last_resp)
}
```

### 步骤 7 — 崩溃处理（`xai-crash-handler`）

**crate 名易错**：不存在 `xai-grok-crash-handler`，真实路径是 `crates/codegen/xai-crash-handler`。crate doc（`lib.rs` 偏移：+0 ~ +32）写明平台差异：Unix 用 `sigaction(2)` 捕 SIGBUS/SIGSEGV/SIGABRT——**捕 SIGABRT 意味着 `panic = "abort"` 构建（所有发行版）在 Rust panic 时也能留下崩溃报告**；Windows 走 `SetUnhandledExceptionFilter` 捕访问违例，且 SIGABRT 捕获是 Unix 专属（Windows 上 `abort()` 不走 unhandled-exception filter）。

## 第四层 · 补全所有逻辑与技术要点

### 4.1 认证 seam 的「为什么」

`xai-grok-auth/src/lib.rs` 的 crate doc（偏移：+0 ~ +1）把动机写死：seam 介于 `xai-file-utils`（持有方）与 `xai-grok-shell`（实现方）之间，目的是**让数据收集器的 import 图里不出现壳层类型**，同时仍能由「刷新感知的 token 解析」驱动 HTTP 请求。这是典型的依赖倒置：数据层依赖抽象（`AuthCredentialProvider`），壳层（现在是 `xai-grok-login`）提供具体实现，二者在运行时组合。

`AuthCredentialProvider: HttpAuth` 的继承关系（`auth_provider.rs` 偏移：+32 的 supertrait 列表）带来一个实用性质：任何持有 `Arc<dyn AuthCredentialProvider>` 的代码既能「解析出当前 bearer」（`snapshot`）也能「往请求注入认证」（`HttpAuth::apply`）——`AuthRetryMiddleware` 只用了前者，OTel exporter 用后者自己组 header map。

### 4.2 401 归因的完整闭环（三处协作）

401 归因不是单点功能，而是三个组件按「同一份尾部片段定义」串起来的：

```
① 定义唯一来源：bearer_fragment::BEARER_SUFFIX_LEN = 12 + bearer_suffix()
   （bearer_fragment.rs:6 / :10）——按「字符」而非字节取尾，非 ASCII 不 panic

② 写入侧：AuthRetryMiddleware::handle → apply_auth_header
   （retry_middleware.rs:58 / :43）
   把 StampedBearerSuffix(bearer_suffix(token)) 插进 http::Extensions

③ 读出侧：execute_with_stamp（retry_middleware.rs:20）
   client.execute_with_extensions(req, &mut ext) 后
   ext.get::<StampedBearerSuffix>().cloned() 返回给调用方

④ 消费侧：StorageClientAttributionBridge::record_401
   （credential_provider.rs:251）
   实现 xai_file_utils::storage_client::Auth401AttributionCallback，
   拿 sent_bearer_prefix 与当前 bearer 比对，判断"是不是我这把 token 被拒"
```

关键不变量（有单测钉）：`StampedBearerSuffix` 记录的是**调用方手上那个响应所对应的** bearer。经历「401 → 刷新 → 重试成功」之后，stamp 必须是新 token 的尾部，而不是第一次尝试的旧 token 尾部（`execute_with_stamp_reports_last_stamped_bearer`）。`apply_auth_header` 在每次重放时都会覆盖 extensions 里的 stamp，所以「最后一次写入者胜出」正好等于「最后那次尝试的 bearer」。

另外，「无凭证 = 无 stamp」（`execute_with_stamp_is_none_when_nothing_stamped`）：归因必须看到「什么都没发」，而不是空字符串或陈旧记录。

### 4.3 token 生命周期状态机

把 `AuthManager` 的判定拼起来，token 的一生有这些状态与迁移：

```
                 ┌──────────────┐
   auth.json ──▶ │ 未加载 (None) │ ── refresh_chain(PreRequest) 冷启动 mint
                 └──────┬───────┘            │
                        │                    ▼
                        │           ┌─────────────────┐
                        └──────────▶│ 内存有效 (fresh) │◀── update() 成功
                                    └────────┬────────┘
                         过期/401            │
                        ┌────────────────────┘
                        ▼
                 ┌──────────────┐  refresh_chain 成功   ┌──────────────┐
                 │ 待刷新 (stale)│ ─────────────────────▶│ 内存有效(新) │
                 └──────┬───────┘                       └──────────────┘
                        │ 刷新失败
                        ▼
                 ┌──────────────────────┐
                 │ permanent_failure 记录 │
                 │ （ScopedRefreshFailure │
                 │  + DualClock 计时）    │
                 └──────┬───────────────┘
                        ├─ snapshot 还活过 SEND_HORIZON(5s) → 仍然返回（grace）
                        ├─ try_adopt_disk_token 成功 → 采纳兄弟进程 token
                        ├─ PERMANENT_FAILURE_TTL(300s) 到 → 自动失效，重试刷新
                        └─ RefreshTokenRejected → requires_manual_reauth()（需重新登录）
```

几个设计点：

- **permanent failure 按 credential 作用域**（`struct ScopedRefreshFailure`，偏移：+111）：结构里有 `token_key`，任何**别的** credential 读过去都是「无失败」，所以失效是自动的，不需要手工清理。
- **双时钟计量**（`recorded_at: DualClock`，注释在偏移：+114 ~ +118）：TTL 是**真实**时间，所以必须跨系统睡眠继续计时；单调时钟在挂起期间暂停，若只用单调时钟，睡前刚缓存的失败会在唤醒后仍然短路 `auth()` 达 5 分钟——而那正是用户回来、期待会话恢复的时刻。
- **`RefreshReason`**（偏移：+50）区分 `PreRequest`（请求前检查，缓存有效就直接用）与 `ServerRejected`（服务端 401/403，必须拿到**不同**的 token）。`DiskTokenDecline`（偏移：+61）把「为什么不采纳磁盘 token」命名成 `Missing` / `Expired` / `LaggingMemoryMint` / `SameKeyAsRejected`，而不是塌缩成一个裸 `None`——注释说明这样调用方能把决策带进结构化日志。
- **`TokenType` 四态分派**：`None` / `ApiKey` / `LegacySession` / `OidcSession | ExternalBinary`，只有后两类走 `refresh_chain`。

### 4.4 遥测的三层过滤与「不能拖慢主流程」

遥测有**三层开关**，逐层收窄：

| 层 | 判定 | 位置 |
|----|------|------|
| 模式 | `TelemetryMode::Disabled` 直接不建 client | `client.rs` `init` 偏移：+13 |
| 事件类别 | `is_enabled()`（仅 `Enabled`）/ `is_session_metrics_enabled()`（含 `SessionMetrics`） | `client.rs` 偏移：+137 / +145 |
| 进程形态 | dev build 默认 `disarm_baked_sinks()`，除非 `GROK_TELEMETRY_ALLOW_DEV_BUILD=1` | `client.rs` `from_config` 偏移：+11 ~ +21 |
| 外发 | `external` 的 settings 门：settings 未解析前 `suppress_external_otel_until_settings()` | `external/mod.rs` 偏移：+288 |

`TelemetryMode` 的语义差被写进注释（`init` 偏移：+415）：`Disabled` 无 client；`SessionMetrics` 有 client 但只有 `session_metrics::*` 事件会发；`Enabled` 全发。`sync_profile` 只在前者（`Enabled`）跑，避免往 Mixpanel 写 people profile。

「不能拖慢主流程」体现在三处：`track` 里 HTTP 与 Mixpanel 的错误都用 `let _ =` / `warn!` 吞掉；`track` 里的 10s timeout 只作用于这一次上报；`sync_profile` 是 `tokio::spawn` 的 fire-and-forget。

**脱敏**在三处独立发生：Sentry 的 `Scrubber`（含 home 前缀与用户名段替换）、Mixpanel 的 `prepare_properties`（先 scrub 再注入 token）、`xai-grok-otel::redact_common`（共享工具，供 span batch redactor 使用）。`TelemetryClient` / `RefreshableSpanExporter` / `AuthManager` 的 `Debug` 实现都刻意只打印布尔或 `"***"`。

### 4.5 崩溃路径的「尽量不做 I/O」

崩溃处理器运行在信号上下文里，能做的操作极其受限，所以设计成**分级**：

| 级别 | API | 做什么 | 何时用 |
|------|-----|--------|--------|
| 最低 | `install_terminal_restore_only()` | 只恢复终端（无文件 I/O、无栈回溯） | `main()` 最早，任何模式 |
| 中 | `enable_terminal_escape_restore()` / `disable_...` | termios + 转义序列，随 TUI 开关升降级 | TUI 模式切换时 |
| 高 | `install(CrashHandlerConfig)` | 完整：信号信息 + 栈回溯 + 写 `last-crash.bin` | 配置开启 `crash_handler_enabled` |

回读侧（`check_previous_crash`）是**普通进程上下文**，所以可以放心做符号化、写报告、归档。文件权限上坚持 0600（`write_owner_only`），因为报告里可能有源码路径与栈帧；归档目录 `history/` 保留最近 5 份。

### 4.6 更新的三条「不变量」

1. **缓存先行，失败不缓存**。`run_update_if_available` 的注释（偏移：+686 ~ +688）明确：「不要在这里写 version.json；只在确认无需更新或安装成功后才缓存。否则一次失败的下载会在 TTL 窗口内压制重试。」
2. **运行中进程 vs 磁盘安装是两个独立判断**。`check_update_background` 里，`current_version`（运行中的二进制）过期只决定「显示重启提示」，`disk_version_for_installer` 才决定「要不要真下载」——这样「退出以更新」路径上的 `grok update` 子进程不会重复下载（注释偏移：+606 ~ +608）。
3. **base URL 可换，但只许换到 loopback**。因为校验是 smoke test 而非 checksum，把 base 指向任意地址等于允许投毒；`GROK_CLI_BASE_URL` 只在真解析后确认 host 是 loopback（含 `localhost` 域、拒绝 userinfo）才生效。

另有一条跨进程协调：`warn_if_other_grok_processes_running()`（偏移：+2319）与 `cleanup_downloads` 的「先确认没有进程在执行」共同避免「正在运行的自已被替换/删除」。

### 4.7 设计不变量小结（本章范围内）

1. **依赖倒置**：数据层依赖 `AuthCredentialProvider` 抽象，`xai-grok-login` 实现，运行期组合；`xai-grok-update` 也直接依赖 login 的 `GrokComConfig` 取 auth scope。
2. **刷新感知 + 归因一致**：token 过期由 `AuthRetryMiddleware` 透明刷新重发（`max_retries = 1`）；`bearer_suffix` 是 401 归因的唯一尾部定义，写入侧与读出侧共用同一份实现。
3. **单点变更**：`AuthManager::apply_refresh_outcome` 是唯一持久化变更点，且用 `&AuthFileLock` 参数在类型层面强制「必须在文件锁下写」。
4. **主动刷新跨睡眠正确**：双时钟计量 + `wake_notify`（`DidWake`）重新武装循环 + 60s 抖动错开兄弟进程。
5. **事件化遥测**：所有关键节点都是 `TelemetryEvent`，名字由 `telemetry_event!` 宏绑定；外部 OTLP 表示集中在 `external/schema.rs` 一个可评审文件。
6. **脱敏默认开启**：Sentry scrubber、Mixpanel scrub-then-inject、OTel span redactor 三处独立生效；所有持密钥类型的 `Debug` 都不落明文。
7. **崩溃分级 + 0600**：信号上下文只做必要 I/O；报告文件强制 owner-only，并会收紧既有宽权限文件。
8. **更新安全**：下载靠 smoke test 校验，因此 base URL 覆盖只允许 loopback；版本缓存只在「确认最新」或「安装成功」后写。
