# 12 · 认证、网络、遥测与更新

> **场景**：grok 要连 LLM API，就得有 token；token 会过期，得刷新；每次请求要带 bearer 并在 401 时重试；整个过程要被遥测记录；产品还要能在后台静默自更新。这四件事（认证 / 网络 / 遥测 / 更新）是「能长期稳定跑起来的 Agent」的运维骨架。
>
> **阅读说明**：源码基准 `SOURCE_REV = d5a0335a47221e8c9519936cb693e9b6450227ec`。四个子系统分别在：`crates/codegen/xai-grok-auth`（认证依赖倒置 seam）、`crates/codegen/xai-grok-shell/src/auth`（壳层认证实现）、`crates/codegen/xai-grok-workspace/src/hub_auth`（Hub 认证）、`crates/codegen/xai-grok-telemetry`（遥测引擎）、`crates/codegen/xai-grok-update`（自更新）。所有 `file:line` 对应当前工作区代码。

## 第二层 · 一个完整例子（全路径走读）

以「用户首次启动 grok 并登录，随后正常跑 Agent」为例：

```
① 启动 → 壳层认证 manager 检查本地是否有可用凭证 (storage.rs)
        │  没有 → 走登录流 flow.rs（device_code / OIDC）
        ▼
② 登录成功 → 拿到 token，存盘 (auth/storage.rs)；发出 Login 遥测事件
   Login 事件结构: xai-grok-telemetry/src/events/mod.rs:376
        │
③ Agent 跑起来，要调 LLM API：
   AuthCredentialProvider::resolve(...) → 当前 bearer
   （xai-grok-auth/src/auth_provider.rs:39 的 trait；壳层 impl 在
    xai-grok-shell/src/auth/credential_provider.rs）
        │
④ 请求经 AuthRetryMiddleware 注入 bearer + stamp：
   execute_with_stamp(...)  retry_middleware.rs:27
   遇 401 → 刷新 token（refresh/ 模块）→ 重试
        │
⑤ 每次关键动作（tool 调用、权限裁决、MCP 错误）发遥测事件：
   TelemetryClient.record(TelemetryEvent)  client.rs:48
   事件实现 TelemetryEvent  events/mod.rs:17
   （如 PermissionOutcome:198、McpErrorType:285、SkillDispatched）
        │
⑥ 后台静默更新检查：
   check_update_background(...)  auto_update.rs:600
   有新版本 → run_update_if_available:685 → 必要时 restart_grok:891
```

链路说明：**token 是贯穿全过程的「通行证」**；认证 seam 让「需要 token 的数据层（xai-file-utils）」不反向依赖「会弹登录 UI 的壳层」；遥测把每个关键节点变成可观测事件；更新让二进制自身保持新鲜。

## 第三层 · 详细逐步说明（主链路拆解）

### 步骤 1 — 认证依赖倒置 seam

`xai-grok-auth` 是个「接缝」（`lib.rs:1-4`）：它把 token 解析定义成 trait，让数据层（如 `xai-file-utils`）只依赖 seam，而不依赖会弹 UI 的壳层类型。

- `trait HttpAuth`（`visibility.rs:5`）——最基础的「往 HTTP 请求注入认证」能力。
- `trait AuthCredentialProvider: HttpAuth + Send + Sync`（`auth_provider.rs:39`）——在 `HttpAuth` 之上加「刷新感知的凭证解析」。
- `CredentialSnapshot`（`auth_provider.rs:14`）——某一时刻的凭证快照。
- `StaticAuthCredentialProvider`（`auth_provider.rs:78`）——静态 bearer 的实现（测试/简单场景）。

### 步骤 2 — 壳层认证实现

`xai-grok-shell/src/auth/` 是 `AuthCredentialProvider` 的真正实现方，模块很全：

- `manager.rs` / `manager/` —— 认证状态机总管。
- `flow.rs` —— 登录流程编排。
- `device_code.rs` —— device-code 登录流（终端无浏览器场景）。
- `oidc/` —— OIDC 登录。
- `refresh/` —— token 刷新（应对过期）。
- `credential_provider.rs` —— 把壳层凭证适配成 `AuthCredentialProvider`。
- `storage.rs` —— token 落盘/读取。
- `jwt.rs` / `token_type.rs` / `token_output.rs` —— token 解析与类型。
- `api_key_probe.rs` / `external_auth.rs` / `attribution.rs` / `recovery.rs` / `config.rs` / `meta.rs` / `single_flight.rs` / `error.rs` / `model.rs` —— 各类辅助（API key 探测、外部认证、单飞防抖等）。

Hub 场景的凭证由 `xai-grok-workspace/src/hub_auth/mod.rs` 提供：`default_auth_path()`(`:86`) 给默认凭证路径，`provider()`(`:385`) 产出 Hub 用的 `AuthCredentialProvider`；`proactive.rs` 负责主动刷新。

### 步骤 3 — 网络层：bearer + 重试中间件

`AuthRetryMiddleware`（`xai-grok-auth/src/retry_middleware.rs:36`）是「认证-aware 的 HTTP 重试」统一入口：

- `new(credentials: Arc<dyn AuthCredentialProvider>, max_retries)`(`:42`)。
- `execute_with_stamp(...)`(`:27`)——在请求上注入 bearer 与一个 stamp（用于幂等/追踪），遇可重试错误（如 401 + token 过期）自动刷新凭证并重发。
- `StampedBearerSuffix`(`:21`)——stamp + bearer 后缀的封装。

MCP 侧的 OAuth 配置在 `xai-grok-config-types/src/mcp.rs`：`McpJsonOAuthBlock`(`:119`)、`oauth_config()`(`:487`) 解析 `oauth_client_id` / `oauth_client_secret_env_var` / `oauth_scopes`，其中 `resolve_oauth_client_secret`(`:19`) 从指定环境变量读 secret（BYO 凭证）。这与第 10 章 MCP 的 `authenticate_mcp_server_dedup`（`xai-grok-mcp/src/oauth.rs:81`）呼应。

### 步骤 4 — 遥测引擎

`xai-grok-telemetry`（`lib.rs:1`）是「产品事件 + Mixpanel 上报 + Sentry 错误 + OpenTelemetry 追踪 + 结构化统一日志」的总入口。模块面：

## 第四层 · 补全所有逻辑与技术要点

### 4.1 认证 seam 的「为什么」

`xai-grok-auth/lib.rs:1-4` 明确：seam 介于 `xai-file-utils`（持有方）与 `xai-grok-shell`（实现方）之间，目的是**让数据收集器的 import 图里不出现壳层类型**，同时仍能由「刷新感知的 token 解析」驱动 HTTP 请求。这是典型的依赖倒置：数据层依赖抽象（`AuthCredentialProvider`），壳层提供具体实现，二者在运行时组合。

`AuthCredentialProvider`（`auth_provider.rs:39`）继承 `HttpAuth`（`visibility.rs:5`），因此任何持有 `Arc<dyn AuthCredentialProvider>` 的代码既能「解析出当前 bearer」也能「往请求注入认证」——`AuthRetryMiddleware` 正是这么用的。

### 4.2 壳层认证的能力面（file 清单）

`crates/codegen/xai-grok-shell/src/auth/` 子模块：

|------|------|
| `manager.rs` / `manager/` | 认证状态机 |
| `flow.rs` | 登录流编排 |
| `device_code.rs` | device-code 登录（无浏览器终端） |
| `oidc/` | OIDC 登录 |

### 4.3 网络重试中间件细节

`AuthRetryMiddleware`（`retry_middleware.rs:36`）：

- `execute_with_stamp(...)`(`:27`)：封装「注入 bearer + stamp → 发送 → 失败按需刷新重发」的逻辑，`max_retries` 由 `new`(`:42`) 设定。
- `StampedBearerSuffix`(`:21`)：把幂等 stamp 拼到 bearer 后缀，便于服务端去重/追踪。
- 重试触发条件通常是「token 过期类 401」——middleware 调 `AuthCredentialProvider` 刷新后重放请求，对调用方透明。

### 4.4 遥测事件模型

所有事件实现 `trait TelemetryEvent: Serialize + Send`（`events/mod.rs:17`），由宏统一实现（`events/mod.rs:31`/`:36`）。代表性事件：

- `Login`(`:376`)：登录成功事件。
- `PermissionOutcome`(`:198`)：权限裁决结果（allow/deny/ask）。
- `McpErrorType`(`:285`)：MCP 错误分类。
- `InstallKind`(`:349`) / `CliUpdateInstaller`(`:132`) / `CliUpdateTrigger`(`:164`)：更新安装相关。
- 技能：`SkillAdded` / `SkillRemoved` / `SkillDispatched`（见 10 章 4.11）。

`TelemetryClient`(`client.rs:48`) 是这些事件的采集/上报总线，下游接 Mixpanel、Sentry、OTel（对应 `http` / `external` / `otel_layer` / `instrumentation` 模块）。

### 4.5 更新流程的可观测与重启

`xai-grok-update/src/auto_update.rs` 的完整生命周期：

1. `check_update_background`(`:600`) → `BackgroundUpdateCheck`(`:571`) / `UpdateAvailable`(`:565`)。
2. 若有 `auto_update_target`(`:364`) 解析目标版本。
3. `download_with_progress`(`:1223`) 或 `download_silent`(`:1283`) 拉取。
4. `install_internal_from_bases`(`:1393`) / `install_internal_from_base`(`:1531`) 安装。

### 4.6 真实函数体拆解（AuthRetryMiddleware）

认证感知的 HTTP 重试不是靠「调用方写循环」，而是把重试逻辑做成一个 `reqwest_middleware::Middleware`，由客户端在发送时自动套用。两个真实函数：

**`execute_with_stamp`**（`retry_middleware.rs:27`，自由函数，非方法）——在发送请求时把实际发出的 bearer 后缀记进 `Extensions`，供 401 归因：

```rust
pub async fn execute_with_stamp(
    client: &reqwest_middleware::ClientWithMiddleware,
    req: Request,
) -> reqwest_middleware::Result<(Response, Option<StampedBearerSuffix>)> {
    let mut ext = http::Extensions::new();
    let resp = client.execute_with_extensions(req, &mut ext).await?;
    Ok((resp, ext.get::<StampedBearerSuffix>().cloned()))
}
```

**`impl Middleware for AuthRetryMiddleware::handle`**（`retry_middleware.rs:64`，真正的 401 重试循环）——`execute_with_stamp` 只是入口；bearer 注入与刷新重发都在这里：

```rust
#[async_trait::async_trait]
impl Middleware for AuthRetryMiddleware {
    async fn handle(&self, mut req, extensions, next) -> Result<Response, Error> {
        if let Some(ref token) = self.credentials.snapshot().token {
            apply_auth_header(&mut req, token, extensions);   // 注入 bearer + 记录 stamp
        }
        let backup = req.try_clone();
        let resp = next.clone().run(req, extensions).await?;
        if resp.status() != StatusCode::UNAUTHORIZED || self.max_retries == 0 {
            return Ok(resp);
        }
        let Some(backup) = backup else { return Ok(resp) };
        let mut last_resp = resp;
        for _ in 0..self.max_retries {
            if !self.credentials.refresh_after_unauthorized().await { break; }  // 刷新 token
            let Some(ref token) = self.credentials.snapshot().token else { break; };
            let Some(mut retry) = backup.try_clone() else { break; };
            apply_auth_header(&mut retry, token, extensions);
            last_resp = next.clone().run(retry, extensions).await?;
            if last_resp.status() != StatusCode::UNAUTHORIZED { return Ok(last_resp); }
        }
        Ok(last_resp)
    }
}
```

要点：(1) 只在 `401` 且 `max_retries > 0` 时进入重试；(2) 每次重试先 `refresh_after_unauthorized` 再重放 `backup` clone，对调用方完全透明；(3) `stamp` 由 `apply_auth_header` 写入 `extensions`，`execute_with_stamp` 在返回里把它带回，调用方据此做 401 归因。

### 4.7 设计不变量小结（本章范围内）

1. **依赖倒置**：数据层依赖 `AuthCredentialProvider` 抽象，壳层实现，运行期组合。
2. **刷新感知**：token 过期由 `AuthRetryMiddleware` 透明刷新重发。
3. **Hub 同源**：Hub 凭证走 `hub_auth::provider`，与本地认证共用同一 seam。
4. **事件化遥测**：所有关键节点都是 `TelemetryEvent`，统一经 `TelemetryClient` 上报。
5. **静默更新**：更新在后台完成，必要时自重启，对用户尽量无感。
6. **安全凭据**：MCP OAuth secret 只从环境变量解析（`resolve_oauth_client_secret`），不落明文配置。
