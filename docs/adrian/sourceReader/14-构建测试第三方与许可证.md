# 14 · 构建、测试、第三方依赖与许可证

> **场景**：grok-build 是个 ~93 crate 的 Cargo workspace，要在多平台编译、要生成 protobuf 代码、要跑分层测试、还要对 vendored 的第三方代码做许可证合规。本章把「怎么从源码变成可运行的 `grok` 二进制、以及合规边界在哪」讲清楚。
>
> **阅读说明**：源码基准 `SOURCE_REV = d5a0335a47221e8c9519936cb693e9b6450227ec`。构建相关在 `crates/build/xai-proto-build` 与各 `build.rs`；测试相关在 `crates/codegen/xai-grok-test-support` 与 `crates/common/xai-test-utils`；第三方依赖 vendored 在 `third_party/`；许可证在仓库根的 `LICENSE` / `SECURITY.md` / `THIRD-PARTY-NOTICES` / `third_party/NOTICE`。所有 `file:line` 对应当前工作区代码。

## 第一层 · 简单框架（系统骨架）

四件事，从「编译」到「合规」：

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ① 构建 (Build)                                                            │
│   Cargo workspace (~93 crates: codegen/common/build + prod + third_party)  │
│   rust-toolchain.toml (1.94.0)                                            │
│   protobuf 代码生成: xai-proto-build (XaiProtoBuilder lib.rs:34)           │
│   各 crate build.rs: xai-grok-shell / xai-grok-tools / pager-bin / version │
└──────────────────────────────────────────────────────────────────────────┘
                ┌─────────────────────────────────────────────────────────┐
                │ ② 第三方 (Third-party) —— vendored 源码                     │
                │   third_party/: dagre_rust / mermaid-to-svg /              │
                │                graphlib_rust / ordered_hashmap + NOTICE   │
                └─────────────────────────────────────────────────────────┘
                ┌─────────────────────────────────────────────────────────┐
                │ ③ 测试 (Test) —— 分层测试支撑                              │
                │   xai-grok-test-support (acp_client/headless/mock_server/  │
                │     sandbox/leader/inference_override)                     │
                │   xai-test-utils (git 辅助等)                         │
                └─────────────────────────────────────────────────────────┘
                ┌─────────────────────────────────────────────────────────┐
                │ ④ 许可证 (License) —— 合规边界                            │
                │   LICENSE / SECURITY.md / THIRD-PARTY-NOTICES /            │
                │   third_party/NOTICE + third_party/README.md               │
                └─────────────────────────────────────────────────────────┘
```

| 子系统 | 入口 | 位置 | 一句话职责 |
|--------|------|------|-----------|
| 构建/代码生成 | `XaiProtoBuilder` | `crates/build/xai-proto-build/src/lib.rs:34` | protobuf → Rust/pbjson 代码生成 |
| 构建脚本 | `build.rs` | `crates/codegen/{xai-grok-shell,xai-grok-tools,xai-grok-tools-api,xai-grok-pager-bin,xai-grok-version}/build.rs` | 编译期生成/校验 |
| 第三方 vendoring | `third_party/` | 仓库根 `third_party/` | 内联托管的第三方 crate |
| 测试支撑 | `xai-grok-test-support` | `crates/codegen/xai-grok-test-support/src/*` | ACP 客户端/无头/桩 server/沙箱/领导选举 |
| 许可证 | `LICENSE` 等 | 仓库根 | 许可证与合规声明 |

## 第二层 · 一个完整例子（全路径走读）

以「开发者改了一处 ACP 协议定义，跑 `cargo build` + `cargo test`」为例：

```
① cargo build
   │  读 rust-toolchain.toml → 锁定 Rust 1.94.0
   │  遍历 workspace 各 crate 的 build.rs
   ▼
② 协议代码生成：
   xai-proto-build 的 XaiProtoBuilder (lib.rs:34)
   按 btree_map/bytes/extern_path/gen_pbjson 等配置 (lib.rs:55-117)
   把 .proto 生成 Rust 类型 + pbjson 序列化代码
        │
③ 编译各 crate → 链接出 xai-grok-pager (安装名 grok)
        │
④ cargo test
   │  测试经 xai-grok-test-support 拉起：
   │   - acp_client.rs 用 TestSandbox 起 grok agent stdio (见 11 章 sandbox)
   │   - mock_server.rs / counting_server.rs 提供桩 MCP/服务
   │   - headless.rs 跑无头 TUI 测试
   │   - leader.rs 测试多实例领导选举
   │   - inference_override.rs 替换推理后端
        ▼
⑤ 合规检查：third_party/ 里 vendored 的代码必须带 NOTICE；
   仓库级 THIRD-PARTY-NOTICES 汇总所有依赖许可
```

链路说明：**构建 = 工具链锁定 + 协议生成 + 编译链接**；**测试 = 用支撑 crate 造可控环境**；**第三方/许可证 = 把外部代码与合规声明管起来**。

## 第三层 · 详细逐步说明（主链路拆解）

### 步骤 1 — 工具链与工作区

- `rust-toolchain.toml` 锁定 Rust 版本（当前 `1.94.0`），保证全平台、全开发者编译一致。
- workspace 分三层目录：`crates/codegen`（业务/工具实现）、`crates/common`（共享基座如 tool-runtime/types/protocol）、`crates/build`（构建期 crate 如 `xai-proto-build`）；外加 `prod/`（发布相关）、`third_party/`（vendored）、`docs/`。

### 步骤 2 — protobuf 代码生成

`crates/build/xai-proto-build/src/lib.rs` 的 `XaiProtoBuilder`(`:34`) 是 protobuf → Rust 的统一生成器（builder 模式）：

- `btree_map`(`:55`) / `bytes`(`:59`)：指定 map/字节字段的 Rust 表示。
- `extern_path`(`:63`)：把外部 proto 路径映射到已有 Rust 路径（避免重复生成）。
- `file_descriptor_set_path`(`:67`)：输出文件描述符集（供反射/校验）。
- `gen_pbjson`(`:72`) / `pbjson_ignore_unknown_fields`(`:77`) / `pbjson_preserve_proto_field_names`(`:86`) / `pbjson_exclude`(`:97`)：生成 pbjson 序列化层及微调。
- `generate_default_stubs`(`:106`) / `honor_debug_redact`(`:112`) / `type_attribute`(`:117`)：默认桩、调试脱敏、类型属性注入。

> ACP（Agent Client Protocol，见 08/09 章）的消息类型就经此生成，保证 TUI 与 Agent 两侧的线格式一致。

### 步骤 3 — 各 crate 的 `build.rs`

以下 crate 带编译期 `build.rs`，在 `cargo build` 时先于主代码运行：

- `crates/codegen/xai-grok-shell/build.rs`
- `crates/codegen/xai-grok-tools/build.rs`
- `crates/codegen/xai-grok-tools-api/build.rs`
- `crates/codegen/xai-grok-pager-bin/build.rs`
- `crates/codegen/xai-grok-version/build.rs`

用途通常是：把版本/commit/资源在编译期嵌进去，或做轻量代码生成与校验。

### 步骤 4 — 测试支撑 crate

`crates/codegen/xai-grok-test-support/src/` 提供可组合的测试原语：

- `acp_client.rs`：用 `TestSandbox` 起 `grok agent stdio`（见 11 章沙箱），是端到端 ACP 测试的主入口。
- `mock_server.rs` / `counting_server.rs`：桩 server（如模拟 MCP / 推理端点）。
- `headless.rs`：无头 TUI 测试（不依赖真实终端）。
- `sandbox.rs`：`TestSandbox`（`xai-grok-test-support/src/sandbox.rs:19`），提供隔离环境、mock URL、沙箱路径。
- `leader.rs`：多实例领导选举测试。
- `inference_override.rs`：替换推理后端（把 LLM 调用换成确定性桩）。
- `env.rs` / `process.rs` / `resources.rs`：环境变量、子进程、测试资源管理。

`crates/common/xai-test-utils/src/` 提供底层工具（如 `git.rs:199` 的 `write_fanout_tree` 造测试 Git 仓库）。

### 步骤 5 — 第三方 vendoring 与许可证

`third_party/` 内联托管了若干第三方 crate（避免外部 registry 漂移）：

```
third_party/
  ├── NOTICE            # 第三方代码许可声明汇总
  ├── README.md         # vendoring 说明
  ├── dagre_rust/       # 图布局（mermaid 渲染依赖）
  ├── mermaid-to-svg/   # mermaid → SVG
  ├── graphlib_rust/    # 图算法
  └── ordered_hashmap/  # 保序哈希表
```

仓库根的合规文件：`LICENSE`（主许可证）、`SECURITY.md`（安全策略）、`THIRD-PARTY-NOTICES`（全部依赖的许可汇总）。

## 第四层 · 补全所有逻辑与技术要点

### 4.1 构建分层

- **工具链锁定**：`rust-toolchain.toml` 固定 1.94.0，CI 与本地一致。
- **协议生成前置**：`xai-proto-build` 在编译早期把 `.proto` 变成 Rust 类型 + pbjson，`extern_path` 复用跨 crate 类型，避免重复生成与版本歧义。
- **编译期嵌入**：各 `build.rs` 把版本/commit/资源在 `cargo build` 时固化进二进制（`xai-grok-version` 的 build.rs 即典型）。
- **产物**：最终链接出 `xai-grok-pager` 二进制，安装名 `grok`（见 07 章入口）。

### 4.2 `XaiProtoBuilder` 配置语义

`xai-proto-build/src/lib.rs:34-117` 的 builder 方法决定生成形态：

| 方法 | 行 | 作用 |
|------|----|------|
| `btree_map` | 55 | map 字段用 `BTreeMap` |
| `bytes` | 59 | bytes 字段表示 |
| `extern_path` | 63 | 外部 proto → 已有 Rust 路径 |
| `file_descriptor_set_path` | 67 | 输出描述符集 |
| `gen_pbjson` | 72 | 生成 pbjson 层 |
| `pbjson_ignore_unknown_fields` | 77 | 忽略未知字段 |
| `pbjson_preserve_proto_field_names` | 86 | 保留 proto 字段名 |
| `pbjson_exclude` | 97 | 排除某些类型 |
| `generate_default_stubs` | 106 | 默认桩 |
| `honor_debug_redact` | 112 | 调试脱敏 |
| `type_attribute` | 117 | 注入类型属性 |

### 4.3 测试金字塔的支撑

- **单元/集成**：普通 `#[test]` / `#[tokio::test]`，辅以 `xai-test-utils`（如造 Git 仓库）。
- **端到端 ACP**：`acp_client.rs` + `TestSandbox` 起真实 `grok agent stdio`，跑完整协议往返。
- **确定性推理**：`inference_override.rs` 把 LLM 换成桩，使测试稳定可重复。
- **多实例**：`leader.rs` 验证领导选举；`mock_server.rs`/`counting_server.rs` 提供可控外部依赖。
- **无头 UI**：`headless.rs` 跑 TUI 逻辑而不依赖终端。

### 4.4 第三方 vendoring 的合规要点

- `third_party/` 下的 crate 是**源码内联**，随仓库版本走，不依赖外部 registry 可用性/版本漂移。
- 每个 vendored 目录需保留其原始许可；`third_party/NOTICE` 汇总；仓库级 `THIRD-PARTY-NOTICES` 覆盖全部（含非 vendored）依赖。
- 修改 vendored 代码需注意其上游许可证约束——`SECURITY.md` 与 `LICENSE` 定义对外承诺。

### 4.5 仓库合规文件一览

| 文件 | 作用 |
|------|------|
| `LICENSE` | 主许可证 |
| `SECURITY.md` | 安全披露策略 |
| `THIRD-PARTY-NOTICES` | 全部依赖许可汇总 |
| `third_party/NOTICE` | vendored 代码许可声明 |
| `third_party/README.md` | vendoring 说明 |
| `CONTRIBUTING.md` | 贡献流程 |
| `clippy.toml` / `rustfmt.toml` | lint/格式化规则 |

### 4.6 设计不变量小结（本章范围内）

1. **工具链锁定**：`rust-toolchain.toml` 固定 1.94.0，构建可复现。
2. **协议单源生成**：`.proto` 经 `xai-proto-build` 统一生成，TUI/Agent 线格式一致。
3. **编译期嵌入**：版本/commit/资源由 `build.rs` 固化。
4. **测试可控**：`TestSandbox` + mock/headless/override 让端到端测试确定性、可重复。
5. **第三方内联**：`third_party/` 源码随仓库走，避免 registry 漂移。
6. **许可证可审计**：`LICENSE` / `THIRD-PARTY-NOTICES` / `third_party/NOTICE` 三层覆盖。
